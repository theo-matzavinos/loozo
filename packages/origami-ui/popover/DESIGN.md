# Popover design map

Ownership and read timing for Popover and the package-private floating presentation (`ɵOrigamiFloating`) this entry point hosts for Popover and Tooltip; `/popover` exports it as a `ɵ` internal. The dismissal layer (`ɵOrigamiLayer`, `ɵOrigamiLayers`) and the presentation contract the floating presentation implements (`ɵOrigamiPresentation`, `ɵOrigamiPresentationScope`) live in `/utils` and are mapped in [utils/DESIGN.md](../utils/DESIGN.md). Usage is in the [README](README.md); the contracts are SPEC sections 10 and 18 and [SPEC-POPOVER.md](../SPEC-POPOVER.md); Tooltip's own map is [tooltip/DESIGN.md](../tooltip/DESIGN.md). The pieces' machines run in effects, render hooks and events, never in a part's host bindings, and aren't mapped here.

## Floating presentation (`ɵOrigamiFloating`)

One per owner (Popover root, Tooltip root), constructed by the owner in its injection context and destroyed last in its teardown. Native manual show/hide of one Content host, preparation, Floating UI positioning and tracking, Presence reveal coordination and the presentation tree.

### Refresh dependencies

- A position result requests a render (`schedule`); its WRITE commits coordinates and the reveal, and Presence's READ in that render discovers the entrance.
- The size properties are written between the READ and the coordinate WRITE, in the calculation's microtasks; a Content resize they cause resets that calculation's rects, so its result already has the final size. Tracking's ResizeObserver then requests another position; with unchanged geometry it writes the same values and resizes nothing.
- A child activates in the render after its parent's reveal commit, which changes the parent's readiness signal its `effect` tracks; the parent also calls each child's `parentRevealed`, which requests a new position.
