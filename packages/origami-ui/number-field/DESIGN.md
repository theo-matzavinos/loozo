# Number field design map

Ownership and read timing. Usage is in the [README](README.md); the contract is SPEC section 30.

```text
OrigamiNumberField (root, a wrapper element)   Options: value, locale, min, max, step,
 │                                              minimumFractionDigits, maximumFractionDigits,
 │                                              useGrouping, disabled, readonly
 │  NumberFieldContext: syntax (formatter + grammar), step math, step count, Input registration,
 │                      focus request, touches, the root's first-render queue of steps and blurs
 │  NumberFieldDraft (lazy): transformedValue(value) ── text ⇄ value, parseErrors ──▶ [formField]
 │  OrigamiNumberFieldState: value, parseErrors, disabled, readonly
 ├─ Input ──register(ngOnInit)──▶ Context (one; a second throws); Field membership (labelable)
 │    attr value = text; edits ──accepts?──▶ Context.edit(text) ──▶ draft ──parse──▶ value
 │                              └─ else undo (text = draft, selection = before the edit)
 │    after every render: element ≠ draft ──▶ element.value; first render of a hydrating Input: adopt the
 │    element's text as an edit, or replace it
 └─ Increment / Decrement ──▶ ogButton (Options from Context.canStep, disabled)
      pointerdown ──▶ its pointerType; mousedown (primary, not after a touch or pen pointerdown)
      ──▶ keep focus in the Input; click ──▶ Context.step(±1)
```

## Refresh dependencies

- An accepted edit writes the draft, which parses it and may write the value; the next render updates the `value` attribute, the buttons' disabled state and State. The Input's after-render sync then finds the element's text equal to the draft and writes nothing.
- A step, a value write or `reset()` changes the value; the draft's `linkedSignal` recomputes the text, and the render after it writes the element's `value` property (the attribute alone doesn't show once the user has edited) and moves a focused Input's caret to the end (where the attribute did show it, Chromium left the caret at the start). The Input remembers the text its last accepted edit left, so the sync after that edit writes nothing.
- Leaving the Input with a whole number refreshes the draft to the value's format without a write; the next render writes the property.
- A change of `syntax` reruns the Context's view effect, which refreshes the draft untracked (clearing its parse errors); its first run only records the syntax, so text replayed at hydration stays.
- Hydration: the Input's first `afterNextRender` and the Context's run after the render that sets the root's `[formField]` binding, the Input's first (default phase), then the Context's (read phase). Replayed `beforeinput`, `input` and composition events aren't parsed, before then or after (the adoption owns the pre-hydration edit), except that the first render records whether it found the text unchanged, adopted it or restored it, and after an unchanged one the first replayed non-composing `input` takes the element's text once (an edit that left the same text); a replayed `compositionstart` or `compositionend` still opens or closes the composition, so one that ends after hydration keeps its text through renders and is checked at its genuine end, and a replayed step or `blur` waits in the Context's queue: a write before it fails in Signal Forms (NG0950). The adoption writes the draft; the queue then steps, touches and reformats in arrival order, and stops once the root is destroyed (a `touch` listener may destroy it): `step` and `left` do nothing on a destroyed root; the next render writes the property.
