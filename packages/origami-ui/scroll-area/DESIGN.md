## Refresh dependencies

- First render: the overflow and Content sizing depend only on registrations, so server HTML has them. When a Scrollbar registers from a child component's view after the Viewport's host bindings ran, the Scrollbar slot's signal refreshes that view in the same change detection: on the client the bindings first write `hidden` and no Content sizing for that axis, then `auto` and the sizing, in the same change detection: SA2 records them in one MutationObserver delivery, so no rendering opportunity falls between them, and railed keeps its box and position (a script reading geometry inside that pass would see them).
- Hydration: Angular's creation pass rewrites a retained node's `style` to its static styles only when it has some (`setupStaticAttributes`, `tNode.styles !== null`), and the bindings write in the update pass, which can follow a layout: eager hydration delivers it separately, and incremental hydration can run it after the triggering event's default action. No part has a static style, so the server's `style` stands until the bindings write the same values: the Viewport keeps its axes and position, and a hydrating key scrolls it as a plain scroller with the same overflow (SA18, SA19). A consumer's static `style` on the Viewport or Content brings the rewrite back for that node: a documented caveat, recorded by SA19.
- Each part's first browser render attaches or observes it and measures at once, so the first frame after attach has geometry. A ResizeObserver callback measures in the next animation frame, so after any observed resize the thumbs show the previous geometry for one frame, and Origami's own thumb writes are observed and settle without a loop error.
- Overflow growth that changes no observed box (inside a fixed-size Content) is measured at the next `pointerenter` on the root or the next `scroll`.
- A direction change without a resize is read at the next measure, scroll, pointer press or wheel. The Viewport's direction normalizes the position (measure, scroll, wheel, a drag's writes, fixed at its press); the track's places the Thumb (each offset write) and maps the pointer (press and each move), and the two are compared at each offset write and move to flip the progress when they differ.
- Incremental hydration: a dormant part isn't constructed, so nothing registers or observes it until its block hydrates; the hydrated server node then registers, attaches and is measured.
