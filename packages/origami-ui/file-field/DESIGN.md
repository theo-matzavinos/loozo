# File field design map

Ownership and read timing. Usage is in the [README](README.md); the contract is SPEC section 33.

## Refresh dependencies

- The Input's mirror tracks the effective value, `adopted` and the Input's pick count: any write to the value (a pick, a drop, the application, a form `reset({ … null })`, a plain replacement signal written from a timer) schedules it through the render effect, with no consumer binding needed. Each genuine pick also schedules it on its own, since the pick changed `files` while the effective value may settle where the mirror last saw it: a replacement signal that undoes the File inside its write leaves the computed value unchanged, and the pick's run then reconciles `files` to it. It finds `input.files[0]` already equal after a pick or adoption, assigns the file after a drop or write, and clears for null. Same-file re-selection depends on that mirror run having happened before the next pick.
- A Clear's write reaches the Input's `files` through the mirror, after the render that may also remove the Clear; the Clear moves focus synchronously in its click, before that render, so focus is on the Input when the consumer's `@if` removes it.
- Touches requested before the root's first browser render are delivered once, in that render's read phase, after every view's default-phase callbacks, so a same-render adoption has written its value first. A held blur depends on its Input's lifetime: if that Input is destroyed before the drain, including in the same render while the root stays, it lapses. A touch with a value write depends only on the root's.
- The zone's drag depth depends on disabled: `data-drag-over` reads it in the render after disabled changes, which discards it, so a drag entered before disabling shows nothing after enabling until its next `dragenter`. A disable and re-enable that no render or zone event reads in between leaves the depth as it was, and the attribute never changed meanwhile.
- A zone's claim of a drag event depends only on dispatch order: the inner zone's handler runs before an enclosing zone's for the same event. Every engine sends the new target's `dragenter` before the old one's `dragleave`, so an enclosing zone's depth counts only the elements of its own area: 0 while the drag is over an inner zone, 1 back over its own area.
- The Field's Labels, State and data attributes depend on the render that follows the Input's registration, as for any Field control (see the [Field design map](../field/DESIGN.md)); on the server too, so server HTML is complete. A Label, Description or Input in a later-hydrating view joins when it registers.
- Hydration: the Input's first `afterNextRender` runs after the render that sets the root's `[formField]` binding; its adoption writes the value once, touches, and sets `adopted`; the mirror's next run finds them equal. A destroyed Input's callbacks don't run, the Context drops a held blur from a destroyed Input, and it ignores calls after the root is destroyed.
