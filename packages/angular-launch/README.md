# @loozo/angular-launch

Typed server functions for Angular applications built with [`@loozo/angular-router`](../angular-router/README.md). You define queries and mutations in an `rpc.ts` file next to a route, and call them from that route's pages and resolvers through a generated, fully typed client.

Calls go through Angular's `HttpClient`. In the browser they're ordinary HTTP requests. During server rendering they run in-process with the current request's context, and hydration reuses their responses through Angular's transfer cache. Errors you declare on a procedure come back typed on the client.

Use it when you want typed reads and writes between an Angular SSR app and its own server, without maintaining a separate API layer.

**Status:** experimental. MIT license. It currently covers queries, mutations, guards and declared errors. There's no builder or watch mode yet, and no subscriptions, optimistic updates, automatic invalidation or storage adapters.

## Requirements

- Angular 22 with SSR: `@angular/core` and `@angular/common` `^22.0.0` and `rxjs` `^7.8.2` (the peer dependencies), plus `@angular/router`, `@angular/ssr` and `@angular/platform-server` as in the example. Tested with Angular 22.2.2.
- `@loozo/angular-router` at exactly the version Launch pins in its `peerDependencies`, as a dependency of your app. Launch generation writes the router's files too, through an internal router entry point, so the two must match; the exact peer dependency enforces that.
- TypeScript 6 with strict checking. Generation rejects a tsconfig where any of `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `strictBuiltinIteratorReturn`, `noImplicitThis` or `useUnknownInCatchVariables` is off, or where `noCheck` is on. `"strict": true` is enough unless a flag is explicitly turned off, including in an extended config. Generation never edits your tsconfig.
- A `package.json` with a `name` in the application directory. The name is part of the generated app identity.

Install both packages:

```sh
pnpm add @loozo/angular-launch @loozo/angular-router@0.0.4
```

## How it fits together

```text
src/
├── context.ts                   defineContext: per-request server context
└── routes/
    ├── route.ts                 defineRoute("")
    └── +authenticated/
        ├── route.ts             pathless route
        ├── rpc.ts               defineRpc("session", …)
        └── todos/
            ├── route.ts         defineRoute("todos")
            ├── rpc.ts           defineRpc("todos", …)
            ├── page.ts
            ├── route.generated.ts  generated by the router
            └── rpc.generated.ts    generated: injectRpc() with session and todos
generated/
├── routes.generated.ts          router: routes for provideRouter
├── destinations.generated.ts    router
├── context.generated.d.ts       registers your context type
└── server.generated.ts          createContext, handleRequest, provideServer
```

Generation writes a `route.generated.ts` and an `rpc.generated.ts` beside every route that has a page or descendants with pages, with or without a local group; the tree shows only the ones for `todos`. Redirect routes, and parents left with only redirects below them, get neither.

The route tree is the router's. An `rpc.ts` belongs to the route declared in the same directory, which must be one of the routes that get these files; generation fails for an `rpc.ts` next to a redirect. Each route's `injectRpc()` exposes its own group and its ancestors' groups. File names are examples: generation finds context and RPC files by their default export, not their name.

## Setup

The [todos example](../../examples/angular-launch/) is a complete app, and the snippets below are simplified from it. `db` and `sessions` stand for your own server-only modules: the example uses a test cookie instead of sessions, and its in-memory `db.todos.listForUser` also takes a test-only delay flag.

### 1. Define the context

One file anywhere in your app's TypeScript sources default-exports `defineContext`. It runs once per live server request and its return value is what every handler and guard receives as `context`:

```ts
// src/context.ts
import { defineContext } from "@loozo/angular-launch/server";
import { db } from "./database.server";
import { sessions } from "./sessions.server";

export default defineContext(async (request: Request) => ({
  request,
  db,
  user: await sessions.authenticate(request),
}));
```

Generation registers the awaited return type, so `Context` from `@loozo/angular-launch/server` is your context type everywhere. Keep per-request state in the context rather than in module-level variables; the context is application-wide in type only.

### 2. Define RPCs next to a route

```ts
// src/routes/+authenticated/todos/rpc.ts
import { defineRpc, mutation, query } from "@loozo/angular-launch/server";
import { isSignedIn, requireUser } from "../../../auth.server";
import { idSchema, titleSchema } from "../../../todo-input.server";

export default defineRpc(
  "todos",
  {
    list: query({
      handler: ({ context }) => context.db.todos.listForUser(requireUser(context).id),
    }),
    add: mutation({
      input: titleSchema,
      handler: ({ input, context }) =>
        context.db.todos.addForUser(requireUser(context).id, input.title),
    }),
  },
  { canActivate: [isSignedIn] },
);
```

### 3. Generate

Generation is a Node function. The example calls it from a small script:

```js
// generate.mjs
import { generate } from "@loozo/angular-launch/generation";

await generate(import.meta.dirname, {
  tsconfig: "tsconfig.app.json",
  scanDirectories: ["src/routes"],
  outDirectory: "generated",
  check: process.argv.includes("--check"),
});
```

Run it before the Angular build. Launch apps use Angular's own `@angular/build:application` builder, not the router's companion builders, which don't accept Launch files:

```json
"scripts": {
  "generate": "node generate.mjs",
  "build": "pnpm generate && ng build"
}
```

Include the generated files, declarations included, in your app tsconfig: `"include": ["src/**/*.ts", "generated/**/*.ts"]`. See [Generation](#generation) for the options and what gets written.

### 4. Wire the browser and server apps

The browser config is ordinary Angular:

```ts
// src/config.ts
import { provideHttpClient } from "@angular/common/http";
import { provideClientHydration } from "@angular/platform-browser";
import { provideRouter } from "@angular/router";
import type { ApplicationConfig } from "@angular/core";
import { routes } from "../generated/routes.generated";

export const config: ApplicationConfig = {
  providers: [provideHttpClient(), provideClientHydration(), provideRouter(routes)],
};
```

The server config adds the generated `provideServer()`, after `provideHttpClient()`:

```ts
// src/config.server.ts
import { mergeApplicationConfig } from "@angular/core";
import { provideServerRendering, withRoutes } from "@angular/ssr";
import { provideServer } from "../generated/server.generated";
import { config } from "./config";
import { rendering } from "./rendering";

export const serverConfig = mergeApplicationConfig(config, {
  providers: [provideServerRendering(withRoutes(rendering)), provideServer()],
});
```

Wrap the server bootstrap in `finishLaunchRendering`. If an RPC is called during prerendering, where there's no live request, this makes the build fail instead of producing a broken page:

```ts
// src/main.server.ts
import { bootstrapApplication, type BootstrapContext } from "@angular/platform-browser";
import { finishLaunchRendering } from "@loozo/angular-launch/server";
import { App } from "./app";
import { serverConfig } from "./config.server";

export default async function bootstrap(context: BootstrapContext) {
  const app = await bootstrapApplication(App, serverConfig, context);

  return finishLaunchRendering(app);
}
```

In the server entry, let `handleRequest` answer RPC requests (it returns `null` for anything else), and render pages with a request scope from `createContext`. This is the Express server that Angular's SSR setup generates, with Launch added:

```ts
// src/server.ts
import { join } from "node:path";
import {
  AngularNodeAppEngine,
  createNodeRequestHandler,
  createWebRequestFromNodeRequest,
  isMainModule,
  writeResponseToNodeResponse,
} from "@angular/ssr/node";
import express from "express";
import { createContext, handleRequest } from "../generated/server.generated";

const browser = join(import.meta.dirname, "../browser");
const angular = new AngularNodeAppEngine();
const app = express();

app.use(express.static(browser, { maxAge: "1y", index: false, redirect: false }));

app.use(async (request, response, next) => {
  try {
    const web = createWebRequestFromNodeRequest(request);
    const rpc = await handleRequest(web);

    if (rpc) {
      await writeResponseToNodeResponse(rpc, response);

      return;
    }

    const scope = await createContext(web);
    const page = await angular.handle(scope.request, scope);

    if (!page) {
      next();

      return;
    }

    await writeResponseToNodeResponse(page, response);
  } catch (error) {
    next(error);
  }
});

if (isMainModule(import.meta.url)) {
  const port = process.env["PORT"] || 4000;

  app.listen(port, (error) => {
    if (error) {
      throw error;
    }

    console.log(`Listening on http://localhost:${port}`);
  });
}

export const reqHandler = createNodeRequestHandler(app);
```

Angular's dev server and build use the exported `reqHandler`; `listen` only runs when you start the built server yourself (see [Deploying](#deploying)). The server must serve the `browser` build output itself: Angular's engine doesn't serve script or style files. Express isn't required; see [Other server frameworks](#other-server-frameworks).

Always pass `scope.request` together with `scope`, not your original request. The scope ties the context to the request Angular renders; if they don't match, RPC calls during rendering fail with `INTERNAL` and a server log entry. This catches wiring mistakes only; it doesn't check your authentication.

## Defining RPCs

`defineRpc(namespace, procedures, options?)` declares a group. Each procedure is a `query` (a read) or a `mutation` (a write):

```ts
query({ input?, canActivate?, errors?, handler });
mutation({ input?, canActivate?, errors?, handler });
```

The handler receives `{ context, input, errors }` and returns a value or a promise.

- **Namespaces and procedure names** are literal ASCII identifiers. `__proto__` is not allowed; `constructor` and `toString` are fine. One `defineRpc` per route; a namespace can't repeat within one route's ancestry, but unrelated branches may reuse it.
- **Inputs** are [Standard Schema](https://standardschema.dev) V1 schemas, from any library or written by hand. Validation can be async and can transform the value: callers pass the schema's input type, and guards and handlers receive its output. The `input` schema must have a concrete type without `undefined` or `null` branches, though its caller input type may be a union such as `Schema<string | number, …>`. Omit `input` for a procedure without input.
- **Guards** return `boolean` or `Promise<boolean>`; `false` fails the call with `FORBIDDEN`. Group guards (in `defineRpc` options) get `{ context, request }`; procedure guards also get the validated `input`. Guards are never inherited through the route tree. A call runs input validation, then the group's guards, then the procedure's guards, then the handler.
- Guards don't narrow types. Use an ordinary function to narrow, such as the example's `requireUser`:

```ts
// src/auth.server.ts
import type { Context, Guard } from "@loozo/angular-launch/server";

export const isSignedIn: Guard = ({ context }) => context.user !== null;

export function requireUser(context: Context): { id: string } {
  if (context.user === null) {
    throw new Error("User required");
  }

  return context.user;
}
```

Availability isn't authorization: anyone who can reach your server can call any procedure, so every group and procedure needs its own guards. Route params aren't passed to procedures automatically; pass what you need as input and validate it.

### JSON values

Inputs and results must be strict JSON. `Date`, `undefined`, `NaN` and `Infinity`, functions, class instances, sparse arrays and cycles are rejected, so convert them explicitly (for example, a date to an ISO string). Rendering and HTTP use the same encoding, so a value that works during SSR also works in the browser. Plain and readonly interfaces work as input and result types without index signatures, and keep their declared types on the client.

### Declared errors

Declare the errors a procedure can return, then throw them from the handler:

```ts
complete: mutation({
  input: idSchema,
  errors: {
    NOT_FOUND: { status: 404, message: "Todo does not exist", data: idSchema },
  },
  handler: async ({ input, context, errors }) => {
    const todo = await context.db.todos.completeForUser(requireUser(context).id, input.id);

    if (todo === null) {
      throw errors.NOT_FOUND({ id: input.id });
    }

    return todo;
  },
}),
```

Each error needs an identifier code, an integer literal `status` from 400 to 599, a non-empty literal `message` and a `data` schema; use a `Schema<null>` for errors without data. The error map must be written inline. The server validates the data with the schema before sending it.

Launch itself uses four codes, which you can't declare:

| Code            | Status | When                                                                                |
| --------------- | ------ | ----------------------------------------------------------------------------------- |
| `INVALID_INPUT` | 400    | Input failed schema validation                                                      |
| `FORBIDDEN`     | 403    | A guard returned `false`, or a mutation was called during server rendering          |
| `RPC_NOT_FOUND` | 404    | No such procedure                                                                   |
| `INTERNAL`      | 500    | Anything else: an unexpected exception, an invalid error payload, a non-JSON result |

`INTERNAL` never exposes details to the client; they go to the server log. Your own `NOT_FOUND` is fine, but `__proto__` can't be an error code.

## Calling RPCs

Each route that has a page or descendants with pages gets an `rpc.generated.ts` with `injectRpc()`, even without its own group; redirect routes don't. Call it in an injection context:

```ts
import { Component } from "@angular/core";
import { injectRpc } from "./rpc.generated";

@Component({/* … */})
export default class Todos {
  readonly #rpc = injectRpc();

  async complete(id: string): Promise<void> {
    try {
      await this.#rpc.todos.complete({ id });
      await this.#rpc.todos.list(); // read again explicitly; nothing is invalidated for you
    } catch (error) {
      if (this.#rpc.todos.complete.isError(error) && error.code === "NOT_FOUND") {
        const missingId: string = error.data.id;
      }
    }
  }
}
```

Every call returns a promise. Procedures with input take the input first and options second; procedures without input take only options:

```ts
await rpc.todos.list();
await rpc.todos.list({ signal, transferCache: false });
await rpc.todos.add({ title }, { signal });
```

| Option          | Effect                                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `signal`        | Abort the HTTP request; the call rejects with an `AbortError`. The server may still finish the work, including a write. |
| `transferCache` | Queries default to `true`. Mutations only accept `false` and never use the transfer cache.                              |

`isError(error)` is true only for errors returned by that exact procedure, and narrows them to its declared errors plus the four framework codes. Network failures and aborts are not `RpcError`s. For a type, use `ClientRpcError<typeof group.procedures.complete>` from `@loozo/angular-launch`. Each callable also has a literal `kind` of `"query"` or `"mutation"`.

Route resolvers can call RPCs too, which is how a page gets its data during SSR:

```ts
// src/routes/+authenticated/todos/route.ts
import { defineRoute } from "@loozo/angular-router";
import parent from "../route";
import { injectRpc } from "./rpc.generated";

export default defineRoute("todos", {
  parent,
  resolve: {
    todos: () => injectRpc().todos.list(),
    session: () => injectRpc().session.current(),
  },
});
```

`Client<typeof group>` from `@loozo/angular-launch` gives you the client type for a group, for example to type a result: `Awaited<ReturnType<Client<typeof group>["list"]>>`. Import the group with `import type` so server code stays out of the browser bundle.

## Server rendering and hydration

During server rendering, calls run directly on the server with the context created for that page request. Queries are stored in Angular's HTTP transfer cache, so hydration reuses the responses instead of calling the server again. After the app is stable, calls are ordinary HTTP requests, each with a fresh context. Opt a query out with `{ transferCache: false }`.

The reuse has limits, all of them Angular's transfer cache behaving as designed:

- Only successful responses transfer. A query that fails during server rendering, with a declared error or a framework code, runs again over HTTP during hydration, with a fresh context. The handler runs twice, and the browser shows whatever the second call returns.
- The cache serves calls made before the app first becomes stable. RPCs called later, for example from a `@defer` block that hydrates on interaction or when it enters the viewport, go over HTTP.
- Launch relies on your app's transfer cache settings. `withNoHttpTransferCache()`, or a `withHttpTransferCacheOptions` `filter` that rejects `/_rpc/` requests, turns reuse off without any error, and every query runs again in the browser.

Mutations are refused during server rendering with `FORBIDDEN`, before validation, guards or the handler run. Rendering should only read.

RPCs need a live request. Prerendering a page that calls an RPC fails the build (with `finishLaunchRendering` in place); static pages that don't call RPCs prerender normally. Blocking initial navigation (`withEnabledBlockingInitialNavigation`) combined with a root resolver that calls an RPC isn't supported.

Transferred responses end up in the HTML. Only return data that the user may see, and serve personalized pages with `Cache-Control: private, no-store`.

## Deploying

With `outputMode: "server"`, `ng build` writes the browser files and a bundled server:

```text
dist/<app>/
├── browser/            scripts, styles and index.csr.html
└── server/server.mjs   your server.ts with Angular, Launch and their dependencies
```

Copy `dist/<app>` to the host and start the server with Node:

```sh
PORT=8080 NG_ALLOWED_HOSTS=example.com node dist/<app>/server/server.mjs
```

The server bundle includes your dependencies by default, so the host doesn't need `node_modules`. `AngularNodeAppEngine` reads two environment variables:

| Variable                 | Effect                                                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `NG_ALLOWED_HOSTS`       | Comma-separated hostnames allowed to render pages, in addition to `security.allowedHosts` in `angular.json`. Pages for other hosts get a 400.                |
| `NG_TRUST_PROXY_HEADERS` | Comma-separated `Forwarded` and `X-Forwarded-*` headers that Angular should trust. Set it only behind a proxy that overwrites those headers. Off by default. |

The host check covers page rendering only. `handleRequest` runs before Angular and answers RPC requests for any host.

Launch calls `/_rpc/<group>/<procedure>` from the root of the domain, even when the app has a different `<base href>`. If the app is served under a path prefix, route `/_rpc/` to the same server.

Browser tabs opened before a deploy keep calling the procedures they were built with. After you move an `rpc.ts`, rename a procedure or change an input schema, those calls fail with `RPC_NOT_FOUND` or `INVALID_INPUT` until the page reloads. The same applies while old and new servers run side by side during a rolling deploy.

Launch has been verified on Node only.

### Other server frameworks

`handleRequest` and `createContext` take a web `Request`, so any framework that gives you one works. `AngularNodeAppEngine` also accepts a web `Request`, and keeps the environment variables above. With [Hono](https://hono.dev) on Node:

```ts
// src/server.ts
import { fileURLToPath } from "node:url";
import { createRequestHandler } from "@angular/ssr";
import { AngularNodeAppEngine, isMainModule } from "@angular/ssr/node";
import { serve } from "@hono/node-server";
import { serveStatic } from "@hono/node-server/serve-static";
import { Hono } from "hono";
import { createContext, handleRequest } from "../generated/server.generated";

const browser = fileURLToPath(new URL("../browser", import.meta.url));
const angular = new AngularNodeAppEngine();
const app = new Hono();

app.use("*", serveStatic({ root: browser }));

app.all("*", async (c) => {
  const rpc = await handleRequest(c.req.raw);

  if (rpc) {
    return rpc;
  }

  const scope = await createContext(c.req.raw);
  const page = await angular.handle(scope.request, scope);

  return page ?? c.notFound();
});

if (isMainModule(import.meta.url)) {
  const port = Number(process.env["PORT"] ?? 4000);

  serve({ fetch: app.fetch, port }, ({ port }) => {
    console.log(`Listening on http://localhost:${port}`);
  });
}

export const reqHandler = createRequestHandler(app.fetch);
```

Export the handler as `reqHandler`; Angular's dev server and build don't look for a default export. Under `ng serve`, `serveStatic` logs that the `browser` directory doesn't exist. That's expected: the dev server serves those files itself.

## Generation

```ts
generate(workspace: string, options: GenerationOptions, stopped?: () => boolean): Promise<void>;
```

| Option            | Type       | Description                                                                   |
| ----------------- | ---------- | ----------------------------------------------------------------------------- |
| `tsconfig`        | `string`   | Your app tsconfig, relative to `workspace`                                    |
| `scanDirectories` | `string[]` | Exactly one route directory, relative to the tsconfig's directory             |
| `outDirectory`    | `string`   | Where the app-wide generated files go, relative to `workspace`                |
| `check`           | `boolean`  | Verify generated files without writing them; fails if anything is out of date |

`workspace` is the absolute path of the application directory (the one with its `package.json`). The tsconfig, scan directory and output directory must all be inside it. `stopped` lets a caller cancel: if it returns `true` before writing starts, nothing is written.

Generation reads your source without running it. It writes the router's files plus:

| File                                    | Contents                                                                         |
| --------------------------------------- | -------------------------------------------------------------------------------- |
| `rpc.generated.ts` beside each route    | `injectRpc()` with the route's own and ancestor groups; none for redirect routes |
| `<outDirectory>/context.generated.d.ts` | Registers your context type                                                      |
| `<outDirectory>/server.generated.ts`    | `createContext`, `handleRequest`, `provideServer`, the registry                  |

Each file starts with an ownership marker comment. Generation only replaces or removes files with those exact names and markers, fails rather than overwrite an unmarked file or a symlink in their place, and removes stale ones. Unchanged files aren't rewritten. Everything is validated before anything is written, so a run that fails validation changes nothing. Files are then written one at a time, with no rollback: a write error partway through, such as an unwritable file, or an interrupted run can leave some files updated and others not. The next successful run repairs them.

Before writing, generation type-checks the generated files, your route and RPC declarations, and any file that directly imports a generated file, using `skipLibCheck: false`. Other files are left to your Angular build.

Generated browser code contains only names, kinds and error metadata, never your schemas, handlers or context. Keep server-only modules out of anything a page imports at runtime; the example names them `*.server.ts`.

`server.generated.ts` binds Launch's internal `createRequestScope`, `handleRpc` and `provideLaunchServer` to your app. It imports them from `@loozo/angular-launch/_server`, an entry point for generated code only that isn't public API and can change in any release; use the generated functions instead. The app identity comes from the `package.json` name, the generation tsconfig's path within the app, and the context file's path and contents, so moving the whole app directory doesn't change it.

Wire IDs come from each group's file path relative to the generation tsconfig's directory. Moving or renaming an `rpc.ts` changes its URL, and moving the generation tsconfig to another directory changes every group's URL. Renaming a namespace or procedure doesn't change the group ID. The example doesn't commit generated files: it regenerates before every build, and `node generate.mjs --check` verifies them without writing.

`@loozo/angular-launch/generation` is Node-only.

### Generation sessions

`generate` starts from scratch on every call. A long-running tool that regenerates repeatedly (for example, after file changes) can create a session instead, which reuses compiler work between calls:

```js
import { createGenerationSession } from "@loozo/angular-launch/generation";

const session = createGenerationSession(workspace, {
  tsconfig: "tsconfig.app.json",
  scanDirectories: ["src/routes"],
  outDirectory: "generated",
});

try {
  await session.generate();
  // …after the next change:
  await session.generate();
  await session.generate({ check: true });
} finally {
  await session.dispose();
}
```

The options are fixed when the session is created. Edits inside the app, including moves, are picked up by the next call; to move the app directory itself, dispose the session and create a new one. A session doesn't watch files and isn't coordinated with Angular's own watcher: you decide when to call `generate`, and must not start a second call before the previous one settles, since overlapping calls are rejected. A failed call doesn't break the session; the next call starts clean. After you change dependencies, create a new session. `dispose()` stops publishing from any active call, waits for it, and makes later calls reject. Don't run two sessions or generators against the same output at once.

## Limitations

- No Angular builder or watch mode for Launch yet; run generation yourself before `ng build` or `ng serve`.
- No subscriptions, optimistic updates, automatic invalidation, or query cache beyond hydration.
- No storage adapters; persistence is your handler's job.
- No production authentication, CSRF, CORS or caching policy. You provide those.
- Server work isn't cancelled when the client aborts, and nothing is rolled back.
- One RPC group per route, and one context per application.
