# @loozo/angular-launch

Launch adds typed server procedures to an Angular application. It builds on `@loozo/angular-router`, the official Angular toolchain and `@angular/ssr`: there is one route tree, one rendering system, and no RPC-specific tree. This document is the product contract; the [README](README.md) shows how to use it. Statements are normative unless marked as examples or limitations. Code samples are illustrative; filenames and names in them are examples.

## Product boundary

Angular owns rendering, hydration, the HTTP pipeline, the transfer cache and the build; `@loozo/angular-router` owns routes, URLs and navigation. Launch adds server steps to route declarations (a route extension), the clients on route handles and server wiring, transports for queries, mutations, streams and channels, and Angular builders that run generation before Angular's own.

### Runtimes

Launch's server code uses web `Request`, `Response`, `AbortSignal` and the standard `WebSocket` only; Node is needed by `/node`, `/generation` and the builders. Supported runtimes: Node, with `@angular/ssr/node` and `createUpgradeHandler` (§Channels "Node glue"); Deno and Cloudflare's workerd, with a platform-neutral server build (`ssr.platform: "neutral"`) whose entry exports `reqHandler` and a function calling `handleUpgrade`, and host glue the README gives:

- **Deno.** `Deno.serve`'s default ("legacy") abort aborts `request.signal` once a request is answered, and synchronously inside `Deno.upgradeWebSocket`, before `accept` (Deno 2.9). The glue passes `handleUpgrade` a copy of the request with its own signal, which follows the original's until `handleUpgrade` settles. It then upgrades, appends `Upgrade.headers` to the upgrade's response and passes the socket to `accept` on `open`; it aborts that signal when `Deno.upgradeWebSocket` throws (Deno also requires `Connection: Upgrade` and `Sec-WebSocket-Key`, which Launch doesn't check), answering 400, and on an `error` event, which is all Deno dispatches for a handshake that fails after the `101`. The same glue holds under `--unstable-no-legacy-abort`.
- **workerd.** The glue accepts the server side of a `WebSocketPair` and answers `101` with `webSocket` and `Upgrade.headers`; the server side's `readyState` is open on `accept`. It needs a compatibility date of 2026-11-17 or later, or on an older date the `enable_request_signal` flag, without which an incoming request's signal never aborts, and before 2026-04-07 also `web_socket_auto_reply_to_close`, without which nothing answers a client's close frame (Launch doesn't). When a client leaves, workerd aborts the request's signal and runs queued microtasks and events, but may cancel the request's timers and I/O unless `ctx.waitUntil` holds them (up to 30 s), which Launch doesn't call; locally a timer set after the client left never fired. A step awaiting cancelled work never resumes, so its `finally` blocks and the code after `next()` don't run. A channel's `messages` ends on the socket's `close` event, so a handler waiting on it returns. workerd's `bufferedAmount` is undocumented and implemented: it rose with a non-reading peer locally (not part of the CI check). Angular's server platform dynamically imports `xhr2`, which Wrangler's bundler must alias.

**Proof.** The example's `verify-runtimes.mjs`, in CI's `launch-runtimes` job, runs its platform-neutral build on Deno (default and `--unstable-no-legacy-abort`) and on workerd under `wrangler dev`, in Chromium: a server-rendered page, an RPC and a cross-origin refusal, a stream and a channel through `connect()`, the raw clients' values, refusals, declared errors and redirect, `break` aborting the handler's signal (and, except on workerd, its return), Deno refusing a handshake it can't complete with 400, a closed page ending a channel's handler, upgrade refusals over HTTP and the call's cookie on the `101`. Node's proof is `verify.mjs` in `launch-browser`. Deployed Workers, Durable Objects and other hosts aren't covered.

## Authored application

```text
src/
└── routes/
    ├── route.ts                 .context(root stage)
    └── +authenticated/
        ├── route.ts             .context(signedIn).use(timing).remote({ session })
        └── todos/
            ├── route.ts         .remote({ todos }).resolve(…)
            ├── page.ts
            ├── destination.generated.ts router-owned
            ├── route.generated.ts router-owned, with Launch's additions
            └── $todoId/
                └── route.ts     .remote({ todo })
```

Launch's `defineRoute` is `createRouteFactory<LaunchSpec>` from the router's `/_core` seam (router SPEC §Route extensions). It offers three contributed steps before the router's own, each at most once and in this order: `.context(stage)`, `.use(...middleware)` (at least one) and `.remote(build)`. All three are `serverOnly`, so route copies strip them; the server reads them from the authored routes `server.generated.ts` imports. A route is a Launch route when its default-exported chain starts at Launch's `defineRoute`, imported from the package root; the router authenticates the factory and generation rejects a route made by any other extension. Generation reads the steps statically and executes no authored module. Namespaces, procedure names and error codes are ASCII identifiers (letters, digits and `_`, not starting with a digit), and `__proto__` is reserved. Explicit schema expressions can't contain absent or nullish branches.

### Route context stages

```ts
// src/routes/route.ts
export default defineRoute("", {}).context(async ({ request }) => ({
  db,
  user: await sessions.authenticate(request),
}));

// src/routes/+authenticated/route.ts
export default defineRoute("", { parent })
  .context(({ context }) => {
    if (context.user === null) {
      throw redirect(signIn, {});
    }

    return { ...context, user: context.user }; // User | null above, User below
  })
  .use(timing)
  .remote(({ query }) => ({
    session: { current: query({ handler: ({ context }) => ({ user: context.user.id }) }) },
  }));
```

- **Input and value.** A stage receives `StageArgs<Context>`: `{ context, request, response, signal }`, where `context` is the result of the stages above it (`{}` at the first), `request` and `signal` are the request scope's (on a channel, the scope's signal follows the upgrade request until `accept`, then the socket; §Channels), and `response` is the response control of the call that first runs the stage. It returns the route's whole context, an object of any type or a promise of one, and the runner keeps that value as the context below, unchanged: Launch doesn't merge, so a stage that adds to the context above spreads it (`{ ...context, user }`), and a key it leaves out is gone. `ChainContext` is the awaited return type of the chain's last stage, `{}` without one.
- **Lazy and memoized.** A request scope (§SSR, hydration and prerendering) runs no stage when it's created. A call runs the stages from the root to the route that declared its namespace, each at most once per scope, through the scope's stage runner; later calls reuse a stage's memoized result, failures included. Stages are per route occurrence: the binding makes one stage per authored route that declares one, so a stage function shared by two routes runs once per route, and a stage always has the same stages above it.
- **Owner prefix.** The stages a namespace runs are fixed when the application is bound, from the declaring route. A deeper page that sees an inherited namespace doesn't change them: the server only sees `/_rpc/<namespace>/<procedure>`.
- **Refusals.** A stage that throws `forbidden()`, `notFound()` or `redirect(destination, values)` answers every call that needs it with that outcome (§Outcomes), so a refusing stage on a pathless route refuses its subtree. Any other exception fails those calls with `INTERNAL`, logged as `Launch context stage failed`; the call's reply internally names the failing stage's route, used for prerender faults (§Prerendering) and never sent. A failure propagates to the stages below unrelabelled: every chain that reuses it reports the stage that threw.
- **No opt-out.** A route can't skip its ancestors' stages. Global module state is not request state; per-request values belong in stages.

### Procedures on routes

```ts
export default defineRoute("todos", { parent })
  .remote(({ query, mutation }) => ({
    todos: {
      list: query({ handler: ({ context, signal }) => context.db.todos.listForUser(context.user.id, { signal }) }),
      complete: mutation({
        input: todoIdSchema,
        use: [ownTodo],
        errors: { NOT_FOUND: { status: 404, message: "Todo does not exist", data: todoIdSchema } },
        handler: async ({ input, context, errors }) => { … },
      }),
    },
  }))
  .resolve({ todos: ({ remote }) => remote.todos.list() });
```

- `.remote(build)`'s argument is a builder callback: an arrow function whose single parameter destructures any of `query`, `mutation`, `stream` and `channel` without renames, defaults or rest, and whose body is a parenthesized object literal of namespaces, each an inline object literal of procedures, each a direct call of one of those bindings with one inline options object. The binding name gives the kind; there's no `kind` field in authored config. Procedure option keys are `handler`, `input`, `use` and `errors` for every kind, plus the required `message` for channels (§Channels). Generation doesn't read `use` contents; TypeScript checks them.
- A route may declare several namespaces. Each namespace is unique across the app, because it names its procedures on the wire (§Wire identity); a duplicate anywhere is a generation error naming the other route.
- The route tree determines available namespaces: the route's own plus its ancestors', including pathless routes. No sibling/descendant traversal API is required.
- Availability is not authorization. An HTTP caller who knows another route's namespace still encounters its stages and middleware.
- A call runs: the owner's stages, the owner's `.use()` middleware with no input (`input` is `undefined`), input validation, procedure middleware with the validated input, then the handler. A refusing stage or route middleware therefore answers before input is validated.
- `middleware(run)`: `run` receives `{ context, input, request, signal, response, next }`. `next()` continues the call and resolves to an opaque token `run` must return; it rejects when anything after it throws, so middleware can wrap the rest of the call. Calling `next` twice, or returning anything other than its result, fails the call with `INTERNAL`, logged. Middleware can't change the context; stages do. `context` is read-only at the top level (type-only). `middleware<Needs = {}, Input = unknown>`: a middleware needs `Needs` and `Input`, given as type arguments or by annotating its argument `MiddlewareArgs<Needs, Input>`; un-annotated it needs nothing, also when written inline in `.use()`, where it doesn't infer the route's context. An entry of `.use()` or a procedure's `use` is a `middleware(run)` definition or a bare `run` function, which Launch runs the same way; a bare function's argument is contextually typed `MiddlewareArgs<RouteContext, unknown>` in `.use()` and `MiddlewareArgs<RouteContext, ValidatedInput>` in a procedure's `use`. Each `.use()` entry must accept the route's context (its own stage included) and `unknown` input; each procedure `use` entry the route's context and the validated input; a misfit, a definition or a function whose annotated argument needs more, fails type checking on the offending entry.
- `.use()` runs only for the declaring route's own procedures: it isn't inherited. There's no dedupe: middleware listed in `.use()` and on a procedure runs twice.
- `forbidden()` returns an `Error` branded with a non-enumerable `Symbol.for("@loozo/angular-launch/outcome/v1")` property, which survives duplicate module copies in the entry and render bundles and can't come from JSON. Thrown from a stage, middleware or a handler it becomes the `FORBIDDEN` frame. `notFound()` and `redirect(destination, values)` carry the same brand (§Outcomes). Declared errors stay handler-only; anything else thrown becomes `INTERNAL`.
- Handlers receive `{ context, input, errors, request, signal, response }` (§Response control). `request` is the live request the call runs in: the scope's copy of the RPC HTTP request, the page request during rendering, or the prerender scope's cookie-less `GET` of the page's URL while Angular prerenders it. Stages and middleware run during rendering too, so request-shaped checks (method, `Sec-Fetch-Site`) don't belong in them.
- Kept router callbacks (`resolve`, guards, `title`) receive `remote`, the route's client, beside the router's own inputs. There are no Launch resolvers. Route params/search values are explicit procedure inputs, never automatically bound or trusted.
- Library routes with server steps are out of scope.

## Validation, values and errors

Input uses Standard Schema V1. The caller supplies the schema's input type; procedure middleware and handlers receive its validated/transformed output. Async validators are supported. Launch does not choose a schema library or invent a schema system. Schemas remain server implementation values unless the app independently imports them.

Results and transmitted inputs are strict JSON-safe. Direct SSR and HTTP apply the same encoding and decoding, not raw server values on only one path. Dates require explicit conversion. Undefined/void, nonfinite numbers, custom prototypes, sparse arrays and cycles are rejected rather than silently advertised as client DTOs. Optional/undefined output fields must be converted to an explicit JSON shape. Received JSON text is held to the same subset: a number literal that overflows to a nonfinite number (`1e400`) is malformed, `INVALID_INPUT` with no issues on the server (HTTP and rendering bodies, a channel's opening input and its message frames) and a `TypeError` on the client (stream event data, channel frames).

Public errors are implemented as procedure-local inline literal declarations: identifier code, nonempty literal message, integer literal status 400–599 and explicit concrete Standard Schema data (including `Schema<null>` for no data). A handler's inferred `errors.NOT_FOUND()` accepts schema input and synchronously creates a throwable, **not** already-validated public data. Shared dispatch awaits validation/transformation and strict-JSON-checks the schema output before publishing. The actual registered procedure owns the factory-failure identity and original declaration, including across native entry/render module duplication. Foreign factory failures, lookalikes, plain exceptions, schema issues/throws and non-JSON schema results produce generic `INTERNAL` and server-only diagnostics.

Input validation failures are field-addressable. `INVALID_INPUT` carries `InvalidInputData` (`{ issues: readonly InputIssue[] }`, both root exports), where each `InputIssue` is exactly `{ path: readonly (string | number)[], message: string }`. Dispatch normalizes the input schema's Standard Schema V1 issues in order: a path segment may be a property key or a `{ key }` segment; strings and finite numbers are kept; an issue with a symbol or any other unrepresentable segment gets the root path `[]` and is never stringified into an invented field. Only path and message are published, never vendor issue fields, input values or stacks, so input schema messages are public and written for users. Malformed requests and envelopes (such as a wrong method, media type or query string, non-JSON bodies, envelopes other than exactly `{ input }`, non-null input without a schema) carry `{ issues: [] }`. Direct SSR and HTTP publish identical issues. `FORBIDDEN`, `RPC_NOT_FOUND` and `INTERNAL` keep `null` data. Stages and route middleware precede validation, so a caller they refuse can't probe input schemas; procedure middleware follows validation and receives the validated input.

A path that names no procedure fails with `RPC_NOT_FOUND`, status 404 and message `"RPC not found"`. The framework codes `INVALID_INPUT`, `FORBIDDEN`, `INTERNAL` and `RPC_NOT_FOUND` are reserved against business declarations, and the object-literal key `__proto__` is unavailable. Business `NOT_FOUND` is ordinary typed data. There's no origin discriminator and no blanket reservation of other business identifiers.

Generated browser metadata includes genuine kind and declared code/status/message only, not runtime schemas, handlers, stages or middleware. Clients validate exact frame shape, strict JSON, known code/status/message and, for framework failures, their exact data (`InvalidInputData` for `INVALID_INPUT`, otherwise `null`), then associate converted `RpcError` instances privately with namespace/procedure ownership. Arbitrary `RpcError` instances and another procedure's failures do not pass `.isError()`. Schema output validation remains server-side; the browser does not reimplement schemas. Procedure-specific `isError()` narrows to a discriminated union of declared schema-output data plus the fixed framework failures: `INVALID_INPUT` with `InvalidInputData`, the others with `null` data:

```ts
try {
  await route.remote.todos.complete({ id: "123" });
} catch (error) {
  if (!route.remote.todos.complete.isError(error)) {
    throw error;
  }

  if (error.code === "NOT_FOUND") {
    console.log(error.data.id);
  }
}
```

TypeScript has no checked exception parameter on `Promise<T>`, so Launch exposes error metadata and type guards rather than claiming automatic catch typing. Network failures, local cancellation and local encoding failures remain distinct from server business failures. The optional TanStack Query integration below consumes operation kinds, identity, results and error metadata without changing this client.

### Outcomes

`notFound()` and `redirect(destination, values)` from `/server` are thrown outcomes, branded like `forbidden()`, for a page that can't be shown. `redirect` is typed exactly as `@loozo/angular-router`'s `createUrl` (`Destination<Target>` and `UrlValues<NoInfer<Target>, SearchKeys>`, from `_core`), takes destinations only and goes to `to = createUrl(destination, values)`, which is root-relative with non-empty, component-encoded segments, so it can't name another origin. A value that isn't a genuine destination of the same `_core` instance (a string, a spread copy, a route, a destination from another package copy) throws `TypeError` at creation, as do values `createUrl` refuses; a codec's own failure propagates. Thrown from a stage or handler, those become `INTERNAL`. The outcome also records `words`: the ordinals of `to`'s path segments that hold the destination's static segments, ascending. `createUrl` writes one path segment per static or scalar segment and per catchall element, in segment order, and for a destination in a named outlet (router SPEC §2) the branch anchor's segments before the group's; the outlet label is no segment. `teams/$team` with `item/$id` in outlet `detail` below it, for team `products`, records `[0, 2]` for `/teams/products/(detail:item/3)`. Dispatch turns outcomes into frames on both transports: `redirect` is status 303 with exactly `{ redirect: { to } }`, or `{ redirect: { to, words } }` when the application binding has `translateSegments` (§Generation and builders) and `words` is non-empty, and no `Location` header (with a null location, fetch returns the response instead of following it), and `notFound` is status 404 with exactly `{ notFound: null }`. Only status 200 is a result: every other status carries a frame dispatch built itself, so a handler result shaped like a frame stays data, and the rendering backend emits `HttpErrorResponse` for every non-200 reply. They aren't framework codes: `RPC_NOT_FOUND` stays the missing-procedure failure, and business `NOT_FOUND` stays declarable. Wrapping middleware sees them as `next()` rejections, like declared errors. A stage that throws one answers the call before any middleware runs.

Clients recognize an outcome frame by exact shape, strict JSON and its own status (and a root-relative `to`), and reject with `RpcRedirect` (with `to`) or `RpcNotFound`, root exports. They aren't `RpcError`s and aren't procedure-owned; `isError()` is false for them, and anything else stays the original error. A redirect's `words`, when present, must be a non-empty array of strictly increasing integers, each less than the number of path segments of `to`, on a path `createUrl` writes. One enumeration (`targetSegments` in `redirect-translation.ts`) reads those segments for validation and translation alike: the path before the first `?` or `#` must be `/`, `/a/b`, `/(outlet:a/b)` or `/a/(outlet:b)`, where every segment is non-empty `createUrl` encoding (the characters `encodeURIComponent` leaves as they are except `(` and `)`, and `%XX` escapes) and the outlet label follows the router's outlet name grammar; segments are counted anchor first, then group, never the label. Matrix parameters, several groups, nested outlets and any other path with `words`, like any other `words`, make the whole frame unrecognized, as any malformed frame is. A frame without `words` keeps any root-relative `to`.

**Translated redirects.** With `translateSegments`, the server stays canonical: live handlers, middleware and stages run in the unlocalized host, where `createUrl` returns source text (§SSR, hydration and prerendering). `provideRedirectTranslation()` from the generated `redirects.generated.ts` provides the private `REDIRECT_TRANSLATOR` (from `/_redirects`) with the build's flat word table: every distinct canonical static word, tagged with the router's own `segmentMessage`, so Angular's inliner gives each localized build its words. The generated client injects it once, at creation, and keeps it in the browser, and on the server only when Angular's `REQUEST` is a `Request` (a live render, the rendering backend's own test); prerender calls run in the localized server application, whose `createUrl` is already localized, so they're never translated. Every recognition of a frame with `words` (query and mutation responses, a stream's start response and error event, a channel's failure frame) passes `to` through it, after Angular's interceptor chain, so interceptors see the wire body on both platforms. The swap decodes the canonical word at each listed segment, replaces it with its translation encoded as `createUrl` encodes (component encoding, `(` and `)` escaped), and keeps every other byte, outlet syntax, search and fragment included; a word missing from the table, or one that doesn't decode, stays canonical. The result must still be root-relative, or the frame is unrecognized. Invariant: in a translated app, `RpcRedirect.to` equals `createUrl(destination, values)` evaluated in the recognizing build, because the router writes one message per distinct canonical word, the destination copies tag each static segment with it, and the table uses the same tags. Which record Angular matches for that URL is the router's; its generation rejects a translation that puts one route's path under a catchall Angular tries first, where the source words don't (router SPEC §10). A request scope created inside a localized server application, which no supported setup does, would translate already-localized text. Without the provider, frames with `words` are recognized and left canonical. URLs inside search values, results, `Location` headers set through `response` and anything the server writes elsewhere stay canonical.

`rpcNavigationErrors({ notFound })` (root export, with `RpcNavigationErrorsOptions`) returns a handler for Angular's `withNavigationErrorHandler`, run in the router's injection context. A navigation whose guard or resolver failed with `RpcRedirect` returns `new RedirectCommand(router.parseUrl(to))`. During SSR, when the final URL then differs from the requested one, Angular's server answers a redirect to it (302, unless the matched server route sets another redirect status). A `skipLocationChange` inherited from an earlier guard redirect can keep the URL, and the page then renders at the request; a navigation that ends in `RpcNotFound` instead renders the not-found page at the requested URL (below). `RpcNotFound` sets `RESPONSE_INIT.status = 404` when provided and returns a `RedirectCommand` to `notFound`, so the not-found page renders at the requested URL; Angular reads `RESPONSE_INIT` after the app is stable. In the browser the command's `browserUrl` is the navigation's URL, and a `skipLocationChange` inherited from a guard's redirect still applies, leaving the address bar where that redirect left it. During SSR (`REQUEST` provided) the URL must end where the request started, because Angular's server answers any other final URL with a redirect, which can't carry the 404 (development throws, production sends an empty 404 with `Location`). When the platform location still holds the request's pathname, search and hash, the command has `skipLocationChange: true` and writes nothing; when an earlier redirect moved it (an `RpcRedirect`, or a guard's redirect, under either `urlUpdateStrategy`), its `browserUrl` is the request's `Location.normalize(pathname) + search + hash`, with `skipLocationChange: false` overriding a skip inherited from a guard's redirect. The browser then repeats the navigation, redirect included, and its address bar ends where that navigation ends. One case still reaches Angular's redirect with the 404: `urlUpdateStrategy: "eager"` with a trusted `X-Forwarded-Prefix` and a request that percent-encodes the start of the prefixed path, since Angular checks the prefix against the raw request but the router has already rewritten the location; production sends an empty 404 with `Location`, which browsers don't follow, and development throws. Before that status, `RpcNotFound` asks the router for the navigation's restore, `currentSearchRestore()` from `@loozo/angular-router/_generated` (router SPEC §7 "Remembered search keys"), with no application option: when the navigation's redirect chain restored a remembered search value and hasn't retried, the handler calls the view's `forget()` and returns `new RedirectCommand(router.parseUrl(originalUrl), { state })` with the current navigation's `state`, and sets no status. The chain continues at the URL it had before the restore, so a restored value that caused the not-found yields the page with its fallbacks: during SSR a 200 at the request URL, carrying the restored values' deletion cookies (§Remembered search keys). A page missing anyway fails again with no restore left and takes the not-found branch, after one retry. `RpcRedirect` never asks, so a redirect keeps remembered values. The retry repeats the navigation, not the request scope. During SSR the retry's calls share the page's scope, whose stage results are memoized with their failures (§Route context stages), so a `.context()` stage whose refusal depends on a remembered value it reads from the request refuses the retry too, and that render answers its rendered 404; hydration's calls then get a fresh scope, after the deletion, and may render the page with its fallbacks while the document's status stays 404. The next fresh document answers 200. A check that depends on a remembered value belongs in a handler that receives it as validated input. A procedure the retry calls again runs again, response effects included, so a handler that sets a cookie sets it twice on the page response. In the browser each retried call is a second RPC. Other errors return `undefined`, Angular's default. Outcomes act only in navigation: elsewhere, calls just reject. An app with its own navigation error handler calls the returned function from it. A server-rendered not-found page calls its procedure again during hydration, because only successful responses transfer; a redirect answered as a redirect doesn't, but one followed by a not-found is part of the rendered page's navigation, so hydration calls both again. Any other guard or resolver failure during SSR, or an outcome without the handler, leaves Angular without a successful navigation, so `angular.handle` returns `null` and the server's fallback answers, without the render's cookies (§Response control); mapping `FORBIDDEN` to a page is out of scope. The root entry imports `@angular/router` and `@loozo/angular-router/_generated` for this, both from peer dependencies, so it needs `@angular/compiler` or the linker in Node.

## Generated client

Generation emits each route's procedure metadata as the route copy's own contribution record (`{ remote: { <namespace>: { methods: [{ name, input, kind, errors }] } } }`) through the router's copy hook, and the copy exports `type Remote = RemoteOf<typeof route>`, `type Context = ContextOf<typeof route>` and, with `tanstackQuery`, `type Queries = QueriesOf<typeof route>`. A copy's type is its authored declaration's, through an erased `import type` of its own `route.ts` (router SPEC §Route extensions), so kept callbacks, `Remote` and the handle members are exactly typed while the copy holds no server code.

```ts
import { injectRoute } from "./route.generated";

const route = injectRoute(); // Inside an Angular injection context.

await route.remote.todos.list();
await route.remote.todos.list({ signal });
await route.remote.todo.get({ id: "123" }, { signal });
```

- **Handle members.** `injectRoute()` and a narrowed `injectActiveRoute()` handle (router SPEC §Active route) carry `remote` and, with `tanstackQuery`, `queries`, as lazy getters from Launch's extension `handle` hook. The first read builds the client from the copy chain's metadata, root first, inside `runInInjectionContext` with the injector captured when the handle was created, and caches it on that handle; a first read outside an injection context, from an event or after an `await`, works. Copying the handle's properties, as a spread does, reads them. An active handle's members use the `injectActiveRoute()` caller's injector, not the route's environment injector: providers a route adds, such as an `HttpClient` interceptor or a route-level `QueryClient`, reach only that route's own `injectRoute()`.
- **Callback input.** Kept router callbacks receive `remote`, built in their own injection context.
- **Calls.** Callables return promises. Input procedures take input then optional call options; no-input procedures take optional options only. Client cancellation unsubscribes HttpClient and rejects with `AbortError`. On the server, the call's stages, middleware and handler see their `signal` abort; "SSR, hydration and prerendering" describes that signal over HTTP and during rendering. Cancellation is advisory: work that doesn't pass the signal on still finishes, and a cancelled mutation may already have committed.
- **Bundles.** Route copies don't import server implementation modules at runtime: stripping a step drops the imports only it used. Every non-redirect Launch route's record in `routes.generated.ts` carries the router's extension stamp, which value-imports the route's copy, so the copies load with the file that owns their records: `main` in an app without lazy route groups. Launch doesn't check what the application's own modules import: keeping server-only modules out of the browser graph is the application's job.

### Wire identity

The namespace is the wire identity of its procedures. It is unique across the app, so the path doesn't depend on effective URLs, source location or scan order: pathless declarations can share URLs, and moving a route doesn't change its procedures' paths. The application binding supplies the real operation kind; the caller cannot relabel a mutation as a query.

```http
POST /_rpc/<namespace>/<procedure>
Content-Type: application/json

{"input":{"id":"123"}}
```

The envelope keeps primitive schema inputs JSON-encoded consistently by HttpClient. The wire format isn't a versioned protocol: a client from one Launch release isn't promised to work with a server from another. Launch sets no size limit on HTTP request bodies; limit them in the host or proxy. Channel frames are limited by `createUpgradeHandler`'s `maxPayload` (§Channels).

### HTTP request checks

The generated `handleRequest(request, { allowedHosts, origins = [] })` (`HandleOptions`, exported from `/server`) answers HTTP RPCs in this order, running no stage before step 5:

1. A path not starting with `/_rpc/` returns `null`.
2. The hostname of `request.url` must match `allowedHosts` as Angular matches its own: exactly, `*.example.com` for subdomains only, or `*`. `allowedHosts` is required and an empty list refuses everything. Otherwise: 400, `text/plain`, `X-Content-Type-Options: nosniff`, body `Host not allowed` (Angular's page behavior, not a Launch frame); the hostname is logged.
3. `POST`, `application/json` and no query string, otherwise `INVALID_INPUT` with no issues.
4. Same origin, otherwise `FORBIDDEN`, logged with the reason: an `Origin` listed in `origins` (exact serialized origins) passes; otherwise a present `Sec-Fetch-Site` must be exactly `same-origin` (`same-site`, `cross-site`, `none` and anything else refuse); otherwise a present `Origin` must equal `request.url`'s origin (`Origin: null` refuses here, but an `origins` entry, `"null"` included, or `Sec-Fetch-Site: same-origin` decides first); a request with neither header is refused. No `Referer` fallback and no opt-out.
5. Request scope creation (which runs nothing and fails only for a request whose body can't be cloned, `INTERNAL`), then body parsing (a body that isn't JSON is `INVALID_INPUT` with no issues, before any stage), then `runProcedure`.

Non-browser callers (curl, scripts, Node `fetch`, server-to-server) must send `Origin`. Browsers send `Sec-Fetch-Site` only to potentially trustworthy origins, so plain-HTTP deployments on other hostnames rely on `Origin`, and behind a proxy that rewrites `Host` the public origin must be listed in `origins`. The same `allowedHosts` array is passed to `AngularNodeAppEngine`, whose explicit list replaces its `NG_ALLOWED_HOSTS` read; `angular.json`'s `security.allowedHosts` stays page-only. Steps 2 and 4 are HTTP-only: server-rendering dispatch carries the page request (`Sec-Fetch-Site` `cross-site` or `none` on ordinary navigations) and isn't checked.

## Response control

Stages, middleware and handlers get `response: ResponseControl` (exported from `/server` with `CookieOptions`): `setCookie(name, value, options?)`, `deleteCookie(name, options?)` and `headers`, a `Headers` object. Its members are function properties, so destructuring is safe. Each transport creates the effects for one call, passes them to `runProcedure` and commits them when it produces its response. A stage writes to the effects of the call that first runs it, once per scope; calls that reuse its result set nothing for it.

- **Cookies.** `setCookie` serializes one `Set-Cookie` value: `name=value; Path=…` then `Domain`, `Max-Age`, `Expires`, `HttpOnly`, `Secure` and `SameSite` as set. Defaults: `path: "/"`, `httpOnly: true`, `secure: true`, `sameSite: "lax"`. The name must be an RFC 9110 token, the value RFC 6265 cookie-octets (no encoding is applied), `path` and `domain` printable ASCII without `;`, `maxAge` an integer, `expires` a valid date, and `sameSite: "none"` needs `secure`; otherwise it throws a `TypeError` (the call fails with `INTERNAL`). `deleteCookie` takes the same options without `maxAge` and `expires`, and sets an empty value with `Max-Age=0` and `Expires=Thu, 01 Jan 1970 00:00:00 GMT`. Cookie prefixes (`__Host-`, `__Secure-`) aren't checked.
- **HTTP.** Once the call reached `runProcedure`, its JSON response carries the call's headers, then Launch's own over them with `set` (`Content-Type`, `Cache-Control`, `Vary`, `X-Content-Type-Options`), then one `Set-Cookie` per cookie, for every outcome: result, declared error, framework failure, `INTERNAL`. Effects aren't dropped on failure, because what a cookie records has usually happened before a later failure, such as a session a stage refreshed before the handler failed; a handler that shouldn't send a cookie on failure sets it after the steps that can fail. Refusals before any stage (host, method, origin, unparsable body) carry none. Status isn't settable.
- **Rendering.** When the call settles, whatever its outcome, the server backend appends its cookies to `RESPONSE_INIT`'s headers (Angular 22 creates them as `Headers`; other `HeadersInit` values are replaced by a `Headers` copy), so they reach the page response and a 302 Angular builds from the same headers; headers are dropped, so a page's headers don't depend on which queries ran. `RESPONSE_INIT` is injected optionally; without it, a call that set cookies fails with `INTERNAL`, logged. Every call in a render shares one request scope, whose stages read the page request, so a cookie one call sets isn't visible to later calls in the render; Launch doesn't rewrite the `Cookie` header. A session refresh in a stage runs once per render; concurrent HTTP requests each have their own scope, so the session store must tolerate concurrent refreshes anyway. A failed initial navigation (`angular.handle` returning `null`) discards `RESPONSE_INIT`, so the render's cookies are lost with the page; Launch doesn't hand them to the server entry. Angular 22.2.2's `renderAngular` awaits `whenStable()` and `handleRendering` then builds the page `Response` from `RESPONSE_INIT`, copying its headers before final serialization, so only calls that settle before the app is first stable deliver cookies; a call made during serialization (`BEFORE_APP_SERIALIZED`) succeeds but its cookies are lost. Launch doesn't detect that case. While Angular prerenders a page there's no `RESPONSE_INIT` and no response: a cookie set then is a prerender fault (§Prerendering), and the reply still reaches the caller.
- **Commit.** Effects commit when the response is produced: when the call settles, or for a stream when its handler returned its iterable (§Streams). After that `setCookie` and `deleteCookie` throw, and changes to `headers` are ignored, so a wrapping middleware's header after `await next()` reaches query and mutation responses and is ignored for streams.
- **Reading.** `readCookies(request)` (from `/server`) parses `request.headers.get("cookie")` into a new `Map`, typed `ReadonlyMap<string, string>`. Pairs are split on `;` only, never `,`, so a value can't carry another pair, and quotes aren't special. Each pair splits at its first `=`, with spaces and tabs (no other whitespace) trimmed around name and value. A pair without `=` or with an empty name is skipped. A repeated name keeps its first occurrence in the header; RFC 6265 §5.4 recommends that browsers send longer paths first, but not all do, and the header carries no Path or Domain, so the reader can't establish which cookie is more specific or where it came from. Values are returned verbatim, quotes and `%` sequences included, matching `setCookie`'s lack of encoding; names and values aren't validated. No header reads as an empty map, as in a prerender scope's cookie-less `GET`. It reads the request it's given, so during rendering it sees the page request, not cookies calls set (Rendering, above). Hosts join repeated `Cookie` fields with `; ` before the request reaches Launch (Node's HTTP/1.1 and HTTP/2 servers, `Deno.serve`), as do Node's `Headers` for appended values; a hand-built `Request` whose `Headers` joins them with `, ` reads as one value.

## Remembered search keys

`searchCookies(options?)` (root export, with `SearchCookieOptions`) returns a storage factory for the router's `provideSearchStorage()` (router SPEC §7 "Remembered search keys") that keeps each remembered search value in a cookie of its own, so a server render reads it from the page request.

- **Cookies.** Each id is stored as `<prefix><id>`, `prefix` defaulting to `"search."`, holding the router's stored text as is, which is cookie-safe. The attributes are `Path=/`, `Max-Age` (`maxAge`, default 31,536,000 seconds: one year), `Secure` (`secure`, default `true`) and `SameSite=Lax`, serialized as §Response control's `setCookie` does, and never `HttpOnly`: the browser reads them through `document.cookie`, so page scripts can too. A forget sets an empty value with `Max-Age=0` and `Expires=Thu, 01 Jan 1970 00:00:00 GMT` and the same `Secure`. `searchCookies` throws `TypeError` for a `prefix` that's neither `""` nor an RFC 9110 token, and a `maxAge` that isn't a positive integer.
- **Server.** Outside the browser platform (`isPlatformBrowser(PLATFORM_ID)`), the factory, which the router runs once per application and so once per render, reads `REQUEST`'s `Cookie` header once with `readCookies`' parsing into an effective map: what the response leaves in the browser. `read` reads the map. A `write` or `forget` that changes it updates it and appends one `Set-Cookie` to `RESPONSE_INIT.headers`, keeping its `Headers` object as the rendering backend does for procedures' cookies (any other `HeadersInit` is replaced by a `Headers` copy), so the value reaches the page response, and a 302 Angular builds from the same headers, beside the cookies procedures set, none replaced. A `write` equal to the map's value and a `forget` of an absent name append nothing, so a page that changes no value sends no `Set-Cookie` for it. The first `read`, `write` or `forget` of a render appends `Vary: Cookie` to the same headers, which Angular merges into a redirect's `Vary`: a page that uses a remembered value answers the visitor's cookies, so a shared cache mustn't reuse it for another visitor. The request is never rewritten: stages and handlers keep reading the page request (§Response control, "Reading"), not the map. Without `REQUEST`, such as while Angular prerenders, the map starts empty; without `RESPONSE_INIT`, writes and forgets update the map and send nothing.
- **Browser.** `read` parses `document.cookie` on every call, and `write` and `forget` set `document.cookie` only when the value changes.
- **Size.** A `write` whose serialized `Set-Cookie` would exceed 4,096 bytes, RFC 6265 §6.1's minimum a browser keeps, isn't written, whatever is stored: the id's stored value, if any, is forgotten instead, so a stale value doesn't come back on the next entry, and in development mode (`isDevMode()`) `console.warn` names the id.
- **Recovery.** `rpcNavigationErrors`' retry forgets the restored values through the router (§Outcomes); their deletions are ordinary forgets.

## SSR, hydration and prerendering

```text
Generated callable → HttpClient → Angular interceptors/transfer cache → backend
  Server backend: runProcedure in the current request scope
  Browser backend: real HTTP request, a fresh request scope
```

A server-only backend adapter keeps Angular's public HTTP pipeline and PendingTasks tracking. It emits ordinary HttpResponse/HttpErrorResponse events. Direct backend execution must use the same validated JSON envelope, serialization and stage/middleware/error pipeline as HTTP.

The generated `createRequestScope(request)` binds the live server request into a `RequestScope` synchronously, running no stage, and the server passes it to Angular's app engine. Angular exposes it via `REQUEST_CONTEXT` in the render-local application. SSR calls run in that scope, sharing its memoized stages; later browser HTTP calls each get a new scope. The scope holds its stage runner and a rendering-call function under a `Symbol.for("@loozo/angular-launch/private-request-scope/v3")` brand. Angular bundles the server entry (`server.mjs`, the `ssr.entry` that creates scopes and answers `/_rpc`) apart from the server application (`main.server.mjs`, which renders), so a module both import, Launch and the authored routes and their imports included, exists once in each bundle. Server code therefore runs in the server entry's copy, for RPCs and for calls made while rendering: the render bundle's backend checks the live scope against its own application binding (same generated identity), then hands the call to the scope's function, which runs `runProcedure` in `"rendering"` mode with the creating copy's binding. The stages, middleware and handlers that answer a page's calls, and the module state they reach, such as an in-memory store or a connection pool, are the ones that answer RPCs. The reply and the runner's results are plain data. While prerendering there's no live scope: the backend creates the render's scope itself, so its calls run in the server application's copy. Server wiring must use `angular.handle(scope.request, scope)`: the generated app identity and a private per-request token bind the scope to Angular's native `REQUEST`, including proxy-sanitization clones and separate entry and render bundles. That catches pairing mistakes, not incorrect authentication or arbitrary server code. Mutations through rendering transport are rejected with the fixed `FORBIDDEN` frame before any stage, middleware, input schema, handler or writes. Both marked generated calls and unmarked local HttpClient calls use the actual procedure kind, without HTTP fallback or scope recreation; caller relabeling or forced transfer-cache options cannot authorize a write. Manual server dispatch defaults to HTTP semantics and has an explicit final `'rendering'` mode. This is not a guarantee that arbitrary application code or external HTTP calls cannot write during rendering.

**Translated segments in the host.** With `translateSegments`, the destination copies the host reaches tag their static segments with `$localize`, but Angular runs no polyfills in the SSR entry, and inlining replaces `@angular/localize/init` in the bundles that do run them with only `(globalThis.$localize ??= {}).locale = "<locale>"`. So the generated `server.generated.ts` first imports the private side-effect entry `@loozo/angular-launch/_source-text`, which installs a source-text tag on `globalThis.$localize` only when it isn't already a function, keeping an existing object's `.locale`. The tag mirrors `ɵ$localize` from `@angular/localize` 22.2 (a `translate` hook applies first; each part's leading `:…:` block is stripped with `\:` escapes honored; parts join with their expressions), pinned by a parity test, and never imports `@angular/localize`, so Angular's "Direct import of '@angular/localize/init'" warning doesn't fire and the localized server applications, which reach `server.generated.ts` too, keep their `.locale`. The guarantee covers modules evaluated through or after `server.generated`: the server entry must import it before any module that reaches a route, or route extraction or the server's start fails with `ReferenceError: $localize is not defined`. The host must stay canonical: a callable `$localize` installed before it is kept, and one that translates (`loadTranslations`, a runtime catalog) is unsupported, because redirect frames then carry translated words at their listed positions, which each build's table either doesn't know (they stay, and that build can't match the URL) or knows as another canonical word (translated again, so the redirect reaches another route's localized path, such as `/anmelden` → `/empfangen`).

Stages, middleware and handlers get an abort `signal`; a stage gets the scope's. Over HTTP it is the scope request's signal, a clone of the incoming request's, so it aborts when the host's `request.signal` does; Angular's Node `createWebRequestFromNodeRequest` signal doesn't abort once the body has been read, so the documented Node server entries link a signal that aborts a microtask after the response closes unfinished: by then `writeResponseToNodeResponse`'s own `close` listener has cancelled a body it was writing, which aborting first would fail, and the helper would log that failure. During rendering it is `AbortSignal.any([pageRequest.signal, perCall.signal])`, where the per-call signal aborts when HttpClient unsubscribes before the call settled; while prerendering, the page request is the prerender scope's, whose signal aborts when the render's application is destroyed. Aborting is advisory: a handler that ignores it still finishes, and a write may already have committed.

Queries default to HttpClient transfer caching and preserve opt-out. Mutation options accept only `transferCache:false`; the generated helper forces false even for untyped callers. Matching requests during hydration reuse the transferred response without network. Angular disables this HTTP cache after browser stability; it is not an ongoing query cache. POST body, URL, method, response type and params must match. Auth/credential/noncacheable-header exclusions and origin mapping require deliberate handling. Only intentionally browser-visible DTOs transfer; the request's context never does. Personalized HTML must not be published through a shared/public cache.

### Prerendering

Angular 22.2 prerenders (`RenderMode.Prerender`, `ɵSERVER_CONTEXT` `'ssg'`) without `REQUEST`, `REQUEST_CONTEXT` or `RESPONSE_INIT`, at `http://localhost:<port>/<path>` when it started the SSR entry on loopback for the build, otherwise `http://ng-localhost/<path>`. Route discovery also boots the app without `REQUEST` (server context `'other'`), and without its root component. The server backend treats both alike; only `finishLaunchRendering` tells discovery apart, by an empty `ApplicationRef.components` (below). Launch doesn't read the private token, and `@angular/ssr`'s public `IS_DISCOVERING_ROUTES` would make `@angular/ssr` a dependency, which Launch doesn't have.

- **Context.** Without `REQUEST`, the server backend resolves targets against the document's URL instead of the page request's and intercepts the same calls; other HTTP requests go to Angular's backend unchanged. The first intercepted call creates the render's scope with `createRequestScope(application, new Request(pageUrl))`, a cookie-less `GET` whose signal aborts when the render's application is destroyed; every call in the render shares it, as in SSR, and `REQUEST_CONTEXT` is ignored. Dispatch is `"rendering"`, so mutations and streams are refused with `FORBIDDEN`. A prerendered page therefore shows what an anonymous visitor sees, like TanStack Start's cookie-less crawl. Not provided: separate build-time stages (two context shapes for procedures to type against) and context-free static procedures (no typed pipeline).
- **Faults.** Every intercepted call that starts before the app is first stable must answer 200 without setting a cookie. Any other reply (refusals before dispatch included), a cookie, or a context stage that throws records the render's first fault, `Launch can't prerender this page: <path> answered <status> <body>` / `<path> set a cookie` / `the context stage of <route file> threw` (with the stage's error as `cause`, recorded before the reply's own fault); the caller still gets the reply (`INTERNAL` for the stage). Outside route discovery, `finishLaunchRendering` awaits `whenStable()`, destroys the application and throws the fault, failing the build, because Angular can log a resolver error, emit no page and still report success (seen on 22.1.5), and a failed `injectQuery` would otherwise render its error state into the file. A call made after that, such as one awaited in a `BEFORE_APP_SERIALIZED` hook, isn't checked: Angular 22.2.2's `renderInternal` runs those hooks after bootstrap returns and passes their errors to the `ErrorHandler`, and the render worker fails a page only when rendering throws, so nothing public can fail the build from there. Its fault is recorded and never read, and the page is written; the README says not to call Launch there, as for cookies during SSR serialization. Live SSR records no faults.
- **After build.** Results reach the browser in the HTML only, through the HTTP transfer cache (keyed by the relative `/_rpc/` URL, so the build's loopback origin doesn't matter) or TanStack dehydration; hydration makes no RPC. Every later call, including a client-side navigation to the page, is an ordinary HTTP RPC in the visitor's own request scope, so queries on prerendered pages should answer the same for everyone. Static deployments (`outputMode: "static"`) can't answer them and are unsupported for pages that call RPCs. Not provided: TanStack-style emitted result files (`staticFunctionMiddleware` writes `/__tsr/staticServerFnCache/<sha1>.json` and the production client always fetches it, with no server fallback), which would need a procedure option, input hashing, worker-to-output plumbing and a rule for inputs that weren't prerendered, and have no consumer; the docs site loads build-time content as generated modules. ISR is out of scope.
- **Dev.** `ng serve` renders prerender routes per request the same way, anonymously.
- **Translated segments.** Prerender calls run in the localized server application, so `createUrl` there returns the locale's words, and its own `server.generated.ts` binding carries `translateSegments`: a prerender redirect frame lists `words` over already-localized text. The client never translates without a live `REQUEST` (§Outcomes), and the redirect is a fault regardless.

Blocking initial navigation (`withEnabledBlockingInitialNavigation`) is supported (checked on Angular 22.2.2). Route discovery calls the server bootstrap with root-component bootstrap disabled, releases the initial navigation to `/` (`afterPreactivation().next()`) only after the bootstrap returns, then awaits `whenStable()` itself. Awaiting `whenStable()` inside the bootstrap would hold that navigation until Angular's 30 s extraction timeout and fail the build, so when `ApplicationRef.components` is empty, which happens only during discovery, `finishLaunchRendering` returns the application at once, without awaiting or reading the render's fault. Resolvers on the routes matching `/`, such as the root route's, then run once during discovery, with the anonymous context above. A refusal there records a fault nothing reads; Angular logs the navigation error, discovery still returns every route and the build succeeds. A prerendered page whose navigation makes the same call still fails the build, and a server-rendered page makes it again with the visitor's context, where it fails like any resolver.

## Streams

A `stream` procedure is a read that sends values while it runs. Its options are a query's; its handler returns an `AsyncIterable` of strict JSON values whose return type is `void` (a non-void return is a type error), written `handler: async function* (args) { … }`. Generation doesn't accept method shorthand in options, so `async *handler()` is rejected. Generated metadata carries `kind: "stream"`; `route.queries` omits streams, and `NamespaceQueries` has no key for them.

**Dispatch.** A stream runs the same pipeline as a query (stages, route middleware, validation, procedure middleware, handler). In `"rendering"` mode it's refused with `FORBIDDEN` before any of it, as mutations are. Over HTTP, `runProcedure` gets a `start` callback: once the handler returns its iterable, the iterator goes to `start` and the innermost middleware step awaits the stream's end, so `next()` resolves when the stream ends, or once the handler returned after its body was cancelled, and rejects with the handler's error. `handleRpc` races the call against `start`: a reply first is an ordinary JSON response with its status (host, method, origin, `RPC_NOT_FOUND`, stage and middleware refusals, `INVALID_INPUT`, a handler that throws or doesn't return an iterable); a start first is a 200 `text/event-stream` response with `Cache-Control: private, no-store, no-transform`, `Vary: Cookie`, `X-Content-Type-Options: nosniff` and `X-Accel-Buffering: no`, plus the call's cookies and headers, which commit then (§Response control). An `async function*` handler's body runs after that commit, so it can't set cookies; stages, middleware before `next()` or a non-generator handler can, and a stage's cookies are in the response's headers before its first event. The call's signal is `AbortSignal.any([scope.request.signal, cancel])`, where `cancel` aborts when the host cancels the body; the body stops when that signal aborts, also when it was already aborted on creation. Angular's `writeResponseToNodeResponse` cancels a body it's writing when the response closes, but skips an already closed response without touching the body, so a client that leaves while stages or middleware run is only noticed through the request's signal: the documented close-signal wiring is required for that case.

**Wire.** The request is the ordinary `POST` envelope; the client also sends `Accept: text/event-stream`. The body is pull-based (a slow reader pauses the generator) and consists of `event: value\ndata: <strict JSON>\n\n` per value, then exactly one `event: end\ndata: null\n\n` or `event: error\ndata: {"status":<n>,"error":{"code","message","data"}}\n\n` once the whole call, middleware included, settled, plus `: keep-alive\n\n` every 15 s, skipped while the reader is behind (the body's queue holds a chunk already), so a stalled reader doesn't grow the queue. The error data is the reply's frame with its status, built by the same failure, declared-error and outcome rules: `{"status":<n>,"error":{…}}`, `{"status":303,"redirect":{"to":…}}` or `{"status":404,"notFound":null}`. An `async function*` handler's body runs only after the response started, so outcomes it throws always arrive this way; middleware and handlers that throw before returning the iterable answer with the ordinary 303/404 JSON response. A value that isn't strict JSON fails the call (`INTERNAL`) and returns the suspended iterator. When the signal aborts, the body stops writing and errors, the handler's in-flight step (if any) is awaited and `iterator.return()` called, which takes effect at the generator's next yield. The handler's part settles once that return does: rejected if the step threw (a `next()` that throws synchronously counts), otherwise resolved, so wrapping middleware never cleans up under a running handler and never misses its failure.

**Client.** A stream callable takes `(input?, { signal }?)` and returns an `AsyncIterable` of the yielded type; each `[Symbol.asyncIterator]()` sends a new request with `fetch` (not `HttpClient`: its requests are `PendingTasks` until they complete, and `FetchBackend` keeps every chunk). Iteration ends on `end`; events that arrived in the same chunk aren't delivered once the signal aborted; throws a procedure-owned `RpcError` for an `error` event or a recognized error response, `RpcRedirect` or `RpcNotFound` for an outcome event or response, an `AbortError` for the signal and a `TypeError` for transport failures, a response whose media type isn't `text/event-stream`, a malformed or unknown event or data that isn't JSON, or a body that ends without `end`; returning early aborts the request. The client injects `PLATFORM_ID` only when its namespaces have streams or channels; on the server platform every iteration fails at once with a procedure-owned `FORBIDDEN` and no request. Interceptors don't apply.

**Reconnection.** None automatic and no resume: iterating again is a new call in a fresh request scope, with its stages, middleware and handler. Handlers yield the current state first. Launch doesn't use EventSource's built-in reconnection, because EventSource can only `GET` without a body, and a same-origin `GET` carries no `Origin`, which the same-origin check needs on plain HTTP.

**Server rendering.** Streams never run while rendering and never enter the HTTP transfer cache. Pages render from a query and follow the stream after hydration; streams add no pending tasks, so an open stream doesn't hold stability, Angular's transfer cache or Launch's TanStack hydration window open.

**TanStack.** No generated options: TanStack's `streamedQuery` (query-core 5.108.4 still exports it as `experimental_streamedQuery`) keeps a query fetching until the stream ends, and `@tanstack/angular-query` adds a pending task while a query is fetching, so an open stream query would keep the app from becoming stable.

**Hosts.** Tested on the built Node server (through `writeResponseToNodeResponse`, with and without the close-signal wiring for a stream already being sent), under `ng serve`, and with a platform-neutral build on Deno and on workerd (§Runtimes, where a handler awaiting a timer or I/O when the client leaves may never resume). Tailscale Serve uses Go's `httputil.ReverseProxy`, which flushes `text/event-stream` immediately; that's known from its source, not tested. Websockets are channels (§Channels).

## Channels

A `channel` procedure talks both ways over one websocket. Its options are a stream's plus a required `message` Standard Schema, held to the same concrete-type rule as `input`; generation requires `message` on channels and rejects it elsewhere. The handler is a stream handler (`async function*`, strict JSON yields, `void` return, no method shorthand) that also receives `messages: AsyncIterable<OutputOf<Message>>`. `Procedure` carries the schema as its fifth type parameter and `message` field, so the client's `send` takes the schema's input type. Generated metadata carries `kind: "channel"`; `route.queries` omits channels and `NamespaceQueries` has no key for them.

```ts
add: channel({
  message: titleSchema,
  handler: async function* ({ context, messages }) {
    yield await context.db.todos.snapshotForUser(context.user.id); // current state first
    for await (const { title } of messages) {                      // validated, in arrival order
      await context.db.todos.addForUser(context.user.id, title);
      yield await context.db.todos.snapshotForUser(context.user.id);
    }
  },
}),
```

**Messages.** Validated with `message` as the handler reads them, one after another so an asynchronous schema can't reorder them. A failed message ends the call with `INVALID_INPUT` and the schema's issues: `messages` throws a `MessageRefused` (internal) that `runProcedure` maps to that reply instead of logging `INTERNAL`, and the socket sends that frame whatever the handler and middleware make of the error. One consumer: a second `[Symbol.asyncIterator]()` throws a `TypeError`. `messages` ends when the socket closes, after the messages already received, so a handler waiting on it returns normally.

**Upgrade checks.** The generated `handleUpgrade(request, options: HandleOptions): Promise<Response | Upgrade | null>` sits next to `handleRequest` and is host-neutral (web `Request` in, a standard `WebSocket` accepted). In order, running no stage before step 5:

1. A path not starting with `/_rpc/` returns `null`, leaving the upgrade to other listeners (Vite HMR).
2. Host, as `handleRequest` (400 text).
3. `GET`, `Upgrade: websocket` and a query of exactly `input` holding strict JSON, otherwise `INVALID_INPUT` with no issues.
4. Same origin, as `handleRequest` (`FORBIDDEN`). Browsers send `Origin` on every handshake.
5. Request scope creation, then `runProcedure` in `"socket"` mode: `RPC_NOT_FOUND` for a path that isn't a channel (and `"http"` mode answers a channel with `RPC_NOT_FOUND`; `"rendering"` refuses it with `FORBIDDEN`), the owner's stages and route middleware, input, procedure middleware, handler.

Steps 2–4 answer with HTTP responses; a browser only sees an error event and close 1006 (a `TypeError` on the client). From step 5 the result is `Upgrade { headers, accept(socket) }`: the call's headers plus one `Set-Cookie` per cookie, the stages' included, committed then (setting a cookie later throws, as in a generator stream's body). A call that failed before its handler returned its iterable (including a stage that throws: `INTERNAL`) also upgrades, and `accept` sends the failure frame and closes 1000, so the client gets the procedure's own error. The call's signal follows the request until `accept`, then the socket closing, never the request (Deno aborts `request.signal` when the socket is upgraded, so its host glue hands `handleUpgrade` a request whose signal stops following the original once `handleUpgrade` settles; §Runtimes). The request scope is created on a copy of the request carrying that signal, so the stages' `signal` and the `request.signal` that stages, middleware and the handler see follow it too. A request that aborts before the handler is reached skips it (an ordinary handler's setup doesn't run either) and the innermost `next()` resolves; one that aborts after the handler returned its iterable stops the started call as a stream's abort does, returning the iterator before its body runs. Either way a socket accepted afterwards is closed at once, without a frame.

**Wire.** `GET /_rpc/<namespace>/<procedure>?input=<encodeURIComponent(strict JSON)>` (`null` without input). Text frames, strict JSON:

```text
client → server  {"message":m}  one message
                 {"ready":n}    "I've read n more values"
server → client  {"value":v}
                 {"ready":n}    "the handler read n more messages"
                 then exactly one {"end":null} or failure frame ({"status":n,"error":{…}} | {"status":303,"redirect":{"to":…}} | {"status":404,"notFound":null}), then close 1000
```

Failure frames are a stream's `error` event data (`failureFrame`). A binary frame, malformed or non-strict JSON, a frame that isn't an object with exactly `message` or `ready`, a message beyond the client's credit, or a grant that isn't a positive integer or exceeds the values outstanding ends the call with `INVALID_INPUT` (no issues); the call's signal aborts, and the frame is sent once the call settled. Frames arriving after the handler finished are dropped.

**Flow control.** Fixed credit windows, not configurable. Values: at most 256 unacknowledged; the client grants `{"ready":k}` once it has read 128 since its last grant. The server pulls the handler's next value only with credit and while the socket's `bufferedAmount` is under 1 MiB, polling every 50 ms while over; the generator stays suspended at `yield` meanwhile, and an abort then returns it at once. Messages: at most 32 unread; the server grants once the handler read 16 since its last grant, but holds the grant back while `bufferedAmount` is at 1 MiB or more, polling every 50 ms, then grants everything read since in one frame; its count of the caller's credit rises only when a grant goes out, so a caller that sends without reading its grants runs out of credit and is refused. Credit 0 on one side implies at least half a window queued on the other, so a grant follows as long as each consumer reads. The raw client can still deadlock when the caller awaits more sends than both windows hold before reading; `connect()` always reads. The Node listener never pauses the socket (`ws.pause()` stops pong and close handling). The 1 MiB mark gates the frames a peer can make Launch produce (values, grants and, on Node, pongs to its pings), so unsent output stays near 1 MiB plus one value frame of any size, one pong and one grant. Two producers aren't gated: the call's terminal frame, whose size the application sets (a refusal carries its schema's issues), and the Node listener's own 15 s heartbeat ping. Incoming is bounded to at most 32 unread messages of up to `maxPayload` each, held as parsed values. On the client, message credit bounds what the socket holds: at most 32 handed frames the handler hasn't read, so the browser's `bufferedAmount` stays within 32 message frames plus its value grants, and the client has no `bufferedAmount` gate. Frames waiting for the socket or for credit are bounded by `send`'s queue (§Channels "Client"). Connection admission and count, the handshake request's size and aggregate budgets are the host's. Throughput is about 256 values per round trip.

**Order and cancellation.** As streams: `next()` of the innermost middleware settles when the handler's part ends; the socket closing (or the request leaving before `accept`) aborts the call's signal, and with it the scope's (the stages' `signal` and `request.signal`), awaits the handler's pending step, returns its iterator and settles, rejecting if the step threw. After the handler ends, the server awaits the whole call's reply, sends the end or failure frame and closes 1000; a message in flight then is dropped.

**Node glue.** `@loozo/angular-launch/node` exports `createUpgradeHandler(handle, { maxPayload = 1 MiB })` returning an `upgrade` listener (its declarations reference only Node types and Launch's `Upgrade`). `ws` 8.21.3 is a regular dependency imported only there; its default `maxPayload` (100 MiB) is replaced, and a bigger frame closes 1009 (client `TypeError`). The listener builds the web `Request` itself (protocol from the socket's `encrypted`, host from `Host`, no proxy headers trusted, as Angular's `createWebRequestFromNodeRequest` default; Launch doesn't depend on `@angular/ssr`) with a signal that aborts on the socket's `end` or `close` until `ws` accepts it: Angular's helper signal never aborts here, and Chromium and WebKit send FIN when they leave early while Firefox sends nothing until accept. `null` leaves the socket alone; a `Response` is written raw (status line, headers, `Content-Length`, `Connection: close`, body) and the socket ends; an `Upgrade` is accepted with `ws` `noServer`, its headers added in the `headers` event, unless the client already left. Accepted sockets are pinged every 15 s and terminated after a missed pong. `ws` answers pings itself without looking at its buffer, so the listener turns that off (`autoPong: false`) and answers a caller's ping at once while the socket's `bufferedAmount` is under 1 MiB; at 1 MiB or more it keeps only the latest ping's payload (RFC 6455 §5.5.3 allows answering only the most recent ping) and sends its pong once `bufferedAmount` is under 1 MiB, polling every 50 ms, so a later ping's pong never overtakes it. The poll stops when the socket closes. Browsers never ping. Creating the listener stores it in the process-global `Symbol.for("@loozo/angular-launch/upgrade-listener/v1")` slot (latest wins), for dev-server forwarding; create it at the server module's top level.

**Client.** A channel callable takes `(input?, { signal }?)` and opens a browser `WebSocket` at once (relative URL, so the page's base URL and `ws(s):`), returning `Channel<Received, Sent>`: an `AsyncIterable` of the yielded type with `send(message): Promise<void>`. `send` rejects `TypeError` once closed, then serializes the frame `{"message":m}` (non-JSON rejects `TypeError`) and queues it in order until the socket is open and credit allows. At most 1,024 frames totalling 1,048,576 UTF-16 code units (`frame.length`) wait at once, fixed: a send whose frame would pass either limit rejects at once with `RangeError("Launch channel send queue is full")` and isn't queued, the channel and the frames already waiting are unaffected, and a later send that fits is accepted; an empty queue accepts one frame of any size. Only frames not yet handed to the socket count. A queued send resolves once handed to the socket, not once delivered, and rejects with the channel's closing error if the channel closes first. One iterator. Values arriving before iteration are held (bounded by the server's window). Iteration ends on `end`; throws the procedure-owned `RpcError`, `RpcRedirect` or `RpcNotFound` for a failure frame (stream recognition), `AbortError` for the signal until iteration ends (queued values are dropped, also after the terminal frame arrived), `TypeError` for a close without a final frame, a refused handshake or a malformed frame. Overlapping `next()` calls settle in order. Leaving the loop or aborting closes 1000. No interceptors and no `PendingTasks`. On the server platform the channel fails at once with procedure-owned `FORBIDDEN` and no connection.

**Signals.** Streams and channels have `connect()`, Launch's own signal object rather than Angular `resource()` (whose `value()` throws in the error state, whose status can't show connecting, and whose reload resets the value). It must run in an injection context. Options: `input` (required with an input schema; without one optional, `null` connecting and `undefined` keeping it closed), `initial`, optional `reduce(state, value)`. It returns `value`, `status` (`"idle" | "connecting" | "open" | "ended" | "failed"`), `error` (`RpcError | RpcRedirect | RpcNotFound | TypeError | Error | undefined`, `Error` being what `reduce` threw, wrapped as an `Error` with it as `cause` when it isn't one), `reconnect()` (after ended or failed) and, for channels, `send()`. On the server platform it never connects: idle, `value` = `initial()`. In the browser it opens from `afterNextRender`, through an effect on `input`: a change closes the current call and opens another; `undefined` closes it and shows idle. It always reads, folding each value through `reduce` untracked from `initial()` for each new call (or taking the latest value without `reduce`). `value` reads `initial()` reactively until the first value; failures and reconnects keep it until the new call's first value. `status` turns `"open"` when the socket opens (a stream: when its response turns out to be an event stream) or a value arrives. `send` delegates while connecting or open and rejects `TypeError` otherwise; a channel's full queue rejects with its `RangeError`, leaving `status` and `error` as they were; one waiting when the call fails rejects with the error `error()` shows, also when `reduce` throws (that fails the call too); one waiting when Launch closes the call, for a new input, `reconnect()` or destruction, rejects with `AbortError`. Its `DestroyRef` closes the call; a call closed for a new input or by destruction doesn't change `status` or `error`. No pending tasks, so an open connection never holds stability.

**Dev server.** Under `ng serve` the serve builder (§Generation and builders) passes Angular's dev server one connect middleware. On the first request through a server it attaches one `upgrade` listener to `request.socket.server` (Vite's HTTP server, which already carries Vite's HMR listener; Vite's own listener answers only `vite-hmr`/`vite-ping` upgrades) and always calls `next()`. That listener forwards upgrades whose raw request target starts with `/_rpc/` to the listener in the process-global slot, which the server module fills each time the dev server loads it, and leaves other upgrades alone. Angular's dev server loads `server.mjs` on an HTTP request that reaches its SSR middleware: the first one, and the first after each server rebuild (the rebuild itself eagerly reloads only `main.server.mjs`, so it doesn't refill the slot). With live reload (the default), the page reload after a server edit is that request, so the new page's channels reach the new module; with `--live-reload=false`, or for an upgrade before any page request since the rebuild, the previously loaded module answers until a page request loads the new one. Channels already open stay on the code they started with. With the slot empty it writes `503`, `text/plain`, `Connection: close` and a short body, after an `error` listener so a reset can't crash the dev server, and warns once per serve run naming `createUpgradeHandler`. A request whose socket exposes no server passes through with one warning that channels aren't forwarded. Upgrades before the dev server's first request aren't forwarded (a browser always loads the page first). The slot key lives in its own internal module, so the builder reads it without loading `ws`.

**Hosts.** Tested on the built Node server and under `ng serve` with Vite's HMR socket still connected, in Chromium, Firefox and WebKit, including the dev-server reload behavior above. `handleUpgrade` is tested on Deno and on workerd with their host glue (§Runtimes). Not tested: Launch's flow control against a slow peer on Deno or workerd (a local experiment only showed workerd's `bufferedAmount` rising with a non-reading peer, §Runtimes), and their pongs (both runtimes answer pings themselves, so the pong bound above is the Node listener's only), and the sizing of the default payload limit. HTTP/2 websockets (RFC 8441) aren't enabled by Node's `http2` by default; browsers fall back to HTTP/1.1. Hono's `@hono/node-server` needs its own upgrade wiring and isn't covered.

Not provided: automatic reconnection or resume, acknowledgements, sharing one socket between calls, binary frames, TanStack options for channels.

## TanStack Query integration

Optional, behind the generation option `tanstackQuery` (default `false`). Off, generated output has no `Queries` type, no `queries` member and no import of the entry. The supported adapter is `@tanstack/angular-query` `^5.0.0`, TanStack's stable Angular adapter, an optional peer dependency; the root and server entries never import it. Releases are tested with 5.108.4, and support covers the tested version. The integration is part of the contract like Launch's other entry points: from 1.0, moving the peer to a new TanStack major is a major release.

`@loozo/angular-launch/tanstack-query` exports `provideLaunchQueries(): EnvironmentProviders`, `type QueriesOf<Route>` and `type NamespaceQueries<Namespace, Procedures>`.

With the option on, each route copy exports `type Queries = QueriesOf<typeof route>`, and its handles carry `queries`: one `NamespaceQueries` per namespace the route sees, built from the copy chain's `{ kind, input }` metadata for queries and mutations. The getter first checks the handle injector for an internal token `provideLaunchQueries()` provides, whose value is the factory, and throws `route.queries requires provideLaunchQueries() from @loozo/angular-launch/tanstack-query in the application providers` on every platform without it; then it builds the factories over the same handle's `remote`, inside `runInInjectionContext` with the captured injector (it injects TanStack's `QueryClient` and the hydration window), and caches them. `remote` works without the provider. The token lets the root entry build `queries` without importing `@tanstack/*`. The core client is unchanged.

Surface per namespace: `$key()`. Per query procedure: `queryOptions(input | skipToken, overrides?)` with input, `queryOptions(overrides?)` without, and `key(input?)`. Per mutation procedure: `mutationOptions(overrides?)` and `key()`. Query and mutation options exist only on their own kind. `$` can't occur in Launch identifiers, so `$key` can't collide.

```text
$key()            ["launch", namespace]
key()             ["launch", namespace, procedure]
key(input)        ["launch", namespace, procedure, input]   input as the caller passed it
queryOptions(…)   the full key, DataTag'd with the procedure's awaited output; skipToken: no input
mutationOptions   mutationKey = key()
```

Generated options:

- `queryFn: ({ signal }) => callable(input?, { signal, transferCache: false })`, respecting no-input arity; `skipToken` input gives `queryFn: skipToken`. `mutationFn` calls `callable(input)` or `callable()`; variables are the caller input, or `void`.
- `retry: (failures, error) => !(error instanceof RpcError || error instanceof RpcRedirect || error instanceof RpcNotFound) && <QueryClient default retry for the query's key>`, resolved per call in query-core's merge order (`getDefaultOptions().queries`, then `getQueryDefaults(queryKey)`). A boolean default applies as is, a number retries while `failures < n`, a function is called with `(failures, error)`, and `undefined` retries while `failures < 3`. So the server keeps the adapter's `retry: false`, and an `RpcError` or outcome never retries.
- `refetchOnMount: (query) => hydrating ? false : <QueryClient default for the query's key, else true>`.
- `structuralSharing: (old, data) => <QueryClient default structuralSharing for the query's key>`, resolved per call in the same merge order as `retry`: `false` returns `data`, a function is called with `(old, data)`, and `true` or `undefined` gives Launch's copy of query-core's `replaceEqualDeep(old, data)` (taken from 5.104.3, unchanged through 5.108.4), which keeps a `"__proto__"` key as own data. `JSON.parse` keeps such a key as own data, but upstream copies keys by assignment, so on a refetch that replaces an object with one holding the key, the setter makes the key's value the copy's prototype and the key is lost (`Object.prototype` itself is never written); upstream won't change it (TanStack/query#12303, closed as not planned). The copy keeps upstream's fast paths, depth limit of 500, `isPlainArray` and `isPlainObject` tests, equality rules and reads (`old[key]` and `data[key]` once each, in the same order), so every result is shared as TanStack's default shares it, with two differences at a `"__proto__"` key: the copy defines it as an own writable, enumerable, configurable data property instead of assigning it, and the old side's value counts only when it's an own property of `old`, so the old object's prototype is never compared or reused. query-core passes `select` output and placeholder data through the same function, so data can be cyclic or hold class instances and getters; those behave as under TanStack's default.
- Overrides replace any default but can't replace the key or the query or mutation function (omitted in the types; applied last at runtime). TError is `unknown`: callers narrow with the callable's `isError`, and the rejection is the callable's own.

Hydration is TanStack's: it dehydrates successful queries into `TransferState` during server rendering and hydrates its browser client before components run. Generated query calls opt out of Angular's HTTP transfer cache, so payloads appear once; direct calls keep the transfer cache. Errors aren't dehydrated: a query that fails during server rendering runs again in the browser.

`provideLaunchQueries()` owns one hydration window per application. It is open in the browser from bootstrap and closed on the server. An `APP_BOOTSTRAP_LISTENER` awaits `ApplicationRef.whenStable()` and then closes it, the hook Angular's HTTP transfer cache uses. The wait must not start from a provider factory, an environment initializer or lazily on first injection: those resolve before bootstrap registers pending work, so the window closes before the first page mounts and every load refetches. With the window, `staleTime: 0` renders server data first with no load-time RPC, and queries mounted after stability follow the client's defaults. The window also opens in a browser app without server rendering: an empty query loads regardless, but one with `initialData` or a pre-seeded cache entry doesn't refetch on mount until first stability.

The `QueryClient` is TanStack's, created per injector by `provideTanStackQuery`'s factory, so each server render has its own cache. Launch owns no client.

Optimistic updates and invalidation are TanStack's own: generated options carry no `onMutate`, `onSettled` or invalidation targets, and Launch owns no `MutationCache`. The guide documents both with the generated keys: per-mutation `invalidateQueries`, an app-wide `MutationCache` `onSettled` that invalidates `["launch"]` once no write that hasn't reached `onSettled` is pending (an `isMutating() > 1` check loses the read when two writes in different scopes settle together), and `onMutate`/`onError` rollbacks driven by the callable's `isError`. Not Launch API: generated invalidate/`setData` helpers, which save one argument per call and re-expose TanStack's filter options, and mutation-declared invalidation targets, which tie server definitions to the client cache and would need Launch to own the settle policy. Declared targets are worth revisiting when a consumer's writes affect other namespaces' queries and invalidating every active Launch query measurably over-fetches.

Not provided: infinite queries, error dehydration, persistence, `@tanstack/angular-query-experimental`, mutation cancellation and `@defer`-specific handling.

## Generation and builders

Launch owns one coordinated generation lifecycle, then delegates to the official Angular builders and dev server. It has no second runtime graph, generic plugin framework or competing watchers.

Generation runs the router's generation through its closed Node-only `@loozo/angular-router/_generation` seam: `discoverLaunchRoutes` (the router's discovery of the scan directory, in Launch mode) and `emitLaunchRoutes(sources, copies, { translateSegments })`, which takes Launch's copy data, type exports and handle members as descriptors. The seam also re-exports the router's `validateLocales`, `segmentMessage`, `Localization` and its builders' `localization` normalizer (as `projectLocalization`), so Launch validates locales, writes message tags and reads `i18n` exactly as the router does, and the router's locale-table pieces (`LocaleWords`, `projectI18n`, `localeTable`, `localeTableWarnings`, `withLocaleTable`, `changedTableWarning`, `checkLocaleTableDefine`, `LocaleTable`), so Launch's builders define the table as the router's do (router SPEC §12, §13). Launch reuses the router's route tree and artifact plan and validates one final overlay before publication. In Launch mode the import rule also admits `server.generated.ts`'s default value imports of routes with a server-only step (router SPEC §Import rule).

The router owns `destination.generated.ts`, `route.generated.ts` (with Launch's descriptors) and `routes.generated.ts`. Launch owns `server.generated.ts` and, with `translateSegments`, `redirects.generated.ts` (its marker is in the router's `launchMarkers`; it's listed among the globals, so turning the option off removes it as stale), replaces or removes only marked outputs, and removes stale ones. The marked `rpc.generated.ts` and `context.generated.d.ts` an earlier version wrote are stale outputs, so the next generation deletes them, and a check reports them as drift. Publication is individual writes, not an atomic transaction against crashes or concurrent writers.

Any release, a patch included, may change generated bytes, and a release supports only the outputs it writes itself, so regenerate and commit after upgrading; check reports drift with the router's regenerate hint (router SPEC §11).

`server.generated.ts` imports every route with a server-only step, in declaration id order (code-unit), and binds them with `bindApplication(<app id>, [entry0, …])`. Each entry is its own `const entryN: Entry = [routeN, "<workspace-relative POSIX file>"];`, where `type Entry = Parameters<typeof bindApplication>[1][number]`, so every route is checked against the binding's route contract without the array literal reducing a union of every route's own type, which grows quadratically with server-step routes. With no server-step route, the binding is `bindApplication(<app id>, [])` and declares no `Entry`. The app identity is a SHA-256 of `launch-app-v2`, the application `package.json` name, and the workspace-relative generation tsconfig and output directory, so it's stable across route edits and workspace moves; it binds request scopes to the application (§SSR, hydration and prerendering).

**`translateSegments`** (default false) needs `localization` (the build's `i18n` and polyfills, `Localization`), and fails generation without it. Before any write it runs the router's `validateLocales`: the `@angular/localize/init` polyfill, and every locale's catalog and translated route tree, failing with the router's `Locale <code>: …` messages. It passes the option to `emitLaunchRoutes`, so copies tag static segments as the router's own builder does; `server.generated.ts` then starts with `import '@loozo/angular-launch/_source-text';` after the marker and binds with `bindApplication(<id>, [...], { translateSegments: true })`. `redirects.generated.ts` imports `redirectTranslation` from `/_redirects` and exports `provideRedirectTranslation()`, whose table function returns `{ words, translations }`: every distinct static segment text of every declaration's local segments, sorted by code unit, and each word's `segmentMessage`, in the same order; the tags evaluate only when a client first needs the table, and the file imports no destination. Generation fails before any write unless some application file outside the generated set and `node_modules` has a value import declaration that resolves to `redirects.generated.ts` and names `provideRedirectTranslation`; it proves the import, not that both applications install it. Off, every byte is today's and no table is written.

Before any cold, update or check publication, strict semantic and provenance checks cover the Launch provenance of every extension route, the builder-callback shape, namespace uniqueness, declared error schemas and schema concreteness. Semantic checking covers generation's own domain: generated outputs, discovered route declarations, and application TypeScript files that directly import a generated output (static import, `export … from`, `import()`, `import()` type or `import =`). Other application files and dependencies get no semantic or syntax diagnostics here (the application's own build reports them); only the scan directory's sources are parsed for discovery, and module-reference and provenance checks still run before publication. The effective TS 6 `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `strictBuiltinIteratorReturn`, `noImplicitThis` and `useUnknownInCatchVariables` must be on, with `noCheck` off. Explicit or inherited false overrides are rejected even with `strict: true`; TS 6 defaults and explicit per-flag true overrides are accepted, without rewriting consumer configs. Literal error maps can't contain duplicate, reserved or invalid codes, invalid fields or nonconcrete schemas. The builder binding, not an authored field, supplies browser metadata and rendering denial, and local and ancestor availability follows real route ancestry.

Launch ships two Angular CLI builders that own that lifecycle, adapted from the router's builders rather than shared through its seam:

- `@loozo/angular-launch:application`: the Launch generation options (`tsconfig`, `scanDirectories`, `outDirectory`, `tanstackQuery`, `translateSegments`, `check`) plus every `@angular/build:application` option. With `translateSegments` it reads `localization` from the target's project and the build's `polyfills` with the router's normalizer, and fails as the router's builder does when it doesn't run as a project target. Its schema is generated from the installed `@angular/build` schema (peer `~22.3.0`) and committed; a test fails when it's stale. It validates options, rejects `watch: true` and an own `define.loozoRouterLocales` (the router's reserved-key message), runs generation once and then schedules `@angular/build:application` with every other option unchanged, except that a localized build (`localize` `true` or a nonempty list, with a project target) gets the router's locale table in `define.loozoRouterLocales`, merged with the build's own `define` and logging the router's relative-base warnings, exactly as the router's application builder adds it (router SPEC §12), from the words generation's `validateLocales` returned (none without `translateSegments`). The builders reach those words through the internal `src/generation/run.ts`; the public `generate()` and sessions still resolve to nothing. A generation failure, including `check: true` drift, is logged and fails the build before Angular's build runs; check mode writes nothing.
- `@loozo/angular-launch:serve`: `@angular/build:dev-server` options plus `poll` (default 1000 ms, forwarded to the dev server, because Angular 22.2's native watcher misses edits inside renamed directories). It reads the generation options from its `buildTarget`, which must use the Launch application builder and must not resolve `check: true`. It uses one generation session: the initial pass must succeed before the dev server starts, otherwise it reports `{ success: false }` without starting it. A watcher on the scan directory triggers sequential passes, and so does the router's `watchConfigInputs` check (router SPEC §13), every 500 ms, of the generation tsconfig, the configs its `extends` chain resolves to or probes, the application's `package.json` (whose `name` is in the app identity) and, with `translateSegments`, every configured catalog file (read from the build target's project and polyfills, like the application builder), wherever each lives, refreshed before every pass, which also catches what the watcher misses inside the scan directory; a catalog edit changes no bytes, so its pass only re-validates and logs a `Locale <code>: …` failure while serving continues; nothing else does, since copies name server types through their declarations, not as text. A pass starts once changes have been quiet for 150 ms (each watcher event serve doesn't skip and each change the check sees restarts that delay), so a save of several files or a directory rename runs one pass, and a change still settling when the initial pass starts is covered by it; changes during a pass cause one more; a config input or catalog inside the scan directory can reach both signals and rarely runs one more pass when a signal settles after a pass has already started, such as a save during a pass (router SPEC §13); an event the router's `isInertFileEvent` (router SPEC §13) finds inert, for a template, style, image, font or Markdown file, causes none under the router serve builder's same conditions (arrived and inspected with no pass running or queued, after a successful last pass), while the check still covers an asset-suffixed generation tsconfig or extended config; events for the router's marked `destination.generated.ts`/`route.generated.ts`/`children.generated.ts` are ignored. A route edit rebuilds twice (the edit, then its regenerated copy), so the first reload can briefly pair new server code with the old copy. A failed later pass is logged and serving continues; the next change retries. The dev server runs through `executeDevServerBuilder` from the `@angular/build` the workspace resolves (as Architect resolves `@angular/build:dev-server`), not `scheduleBuilder`, so it can take the channel-forwarding middleware (§Channels); its options are first validated and defaulted against that builder's schema with `context.validateOptions`, and its outputs are forwarded as the builder's. Risk: Angular 22.2 marks `executeDevServerBuilder` `@experimental` and its `extensions` (middleware) as not supported, so an Angular update can break serving. Angular adds its own teardowns (closing Vite's server, aborting the build's watch) to the context it runs in, and Architect runs a context's teardowns only on a Stop, so the dev server gets a copy of the context whose `addTeardown` collects them, and the builder's stop runs them once whether Architect stops it, the dev server fails or it ends on its own. Teardown closes the watcher and the config check, runs those teardowns, ends the dev server's iteration and disposes the session; a dev server that fails errors the builder, and one that ends on its own completes it. The locale table is the router serve builder's (router SPEC §13): an own `define.loozoRouterLocales` in the serve options or the build target fails before the watcher starts; a build target whose `localize` is a single-locale list gets the table of the initial pass's words, with the served locale at the build's `baseHref` (else `/`), merged into the dev server's `define` before its options are validated; any other `localize` gets none. A later successful pass whose table differs logs the router's `Locale words changed (…)` warning once per distinct table; the running dev server keeps its started table.

## Testing

`callProcedure(route, namespace, procedure, { context, input?, request? })` from `/testing` runs one query or mutation of a route in a test, without HTTP, and settles to `ProcedureCall`: the reply as the client would receive it.

- **Route and namespace.** `route` is an authored route made by Launch's `defineRoute`, or a route below one. Its own record, the last of its contribution chain, must declare `namespace` in its `.remote()`: production binds each namespace to its declaring route's stages and `.use()` (§Route context stages), so an ancestor's namespace is called through the ancestor's route, and a route copy declares none. A route without a Launch chain, a namespace the record doesn't declare, an unknown procedure, a stream or a channel is a `TypeError`; the parameter types reject them too (`procedure` takes query and mutation names only).
- **Context.** The chain's first record is the root: the topmost route that uses a Launch step. Its `.context()` stage never runs; `context` stands in for its value, typed as that record's `ChainContext` (`{}` without a stage). The stages of every later record run as in production, root first, in a fresh request scope created like the generated `createRequestScope`'s. The root's own `.use()` and namespaces run normally when it's the declaring route.
- **Pipeline.** The call then runs `runProcedure` in `"http"` mode with the envelope `{ input }` (`input` defaults to `null`): the declaring route's `.use()`, strict JSON, validation, the procedure's middleware, the handler, outcomes and declared errors, with the replies §Procedures on routes and §Outcomes define. No host, origin, method or content-type check (§HTTP request checks) and no rendering-mode refusal apply; those stay tested through `handleRequest`.
- **Request.** `request` defaults to `POST http://localhost/_rpc/<namespace>/<procedure>` with no body. Stages, middleware and the handler receive the scope's copy of it and its signal. A request whose body was already read rejects the call.
- **Result.** Status 200 settles to `{ status: 200, result }`; any other reply to `{ status, ...frame }` with its `error`, `redirect` or `notFound` frame. Its binding has no `translateSegments`, so a redirect is exactly `{ to }`, never `words`, with `to` from the destination copies the test's graph imports (source text under `@angular/localize/init` without catalogs). Both carry `cookies`, the `Set-Cookie` values in the order set, and `headers`, the call's own headers without Launch's response headers; the effects commit when the call settles. Results and error data are strict JSON parsed back, as on the wire. An unexpected failure settles to `INTERNAL`, logged as `runProcedure` logs it; `RPC_NOT_FOUND` can't result.

## Threat model

What Launch protects, against whom, and what it leaves to the host and the application. The sections above specify each mechanism; this one states what it proves and what it doesn't. A residual risk the consumer must handle is rated criticality / likelihood (low, medium, high or critical / unlikely, possible, likely or certain) for an application that doesn't handle it.

**Assets.** The application's data and the writes procedures make; the user's session, which browsers attach to requests as cookies; the server's memory, CPU and connections; secrets and server code, which must stay out of the browser build; and the integrity of what the browser client reports as results, failures and outcomes.

**Trust boundaries.**

1. Network → host. Any client reaches the host's HTTP server. The host, its proxies and the Node listener (§Channels "Node glue") build the web `Request`; Launch checks the URL and headers it's given and reads no proxy header itself. Proxies must pass `Origin` and `Sec-Fetch-Site` through unchanged.
2. Request → checks. `handleRequest` and `handleUpgrade` check host, shape and origin before any authored code runs (§HTTP request checks, §Channels "Upgrade checks").
3. Checks → application code. Stages, middleware, schemas and handlers are trusted code receiving untrusted input.
4. Server → browser. The browser client trusts the origin that served the page to answer its relative `/_rpc/` calls.
5. Source → builds. Authored sources, the toolchain and dependencies are trusted; the browser build they produce is public.

**Network callers.** A caller outside a browser sends any method, target, header and body, `Host`, `Origin` and `Sec-Fetch-Site` included, so it passes the host and same-origin checks at will. Those checks are browser CSRF signals, not authentication: `allowedHosts` isn't a network ACL, and a passing origin says nothing about who is calling. Every namespace is a public address: any caller can reach `/_rpc/<namespace>/<procedure>`, whichever pages use it (§Procedures on routes). Stages own authentication and authorization; route middleware can refuse too. The order is part of the contract: no stage runs before the checks; body parsing and procedure lookup follow them, before any stage; the owner's stages and route middleware run before input validation, so a caller they refuse never reaches a schema; procedure middleware and the handler see only validated input. Authorization in procedure middleware or the handler lets any caller run validation first and read its issues. Issue messages and declared errors are public; unexpected errors reach the server log only, unescaped. Risk: a procedure whose owner has no refusing stage or route middleware answers anyone, high / possible.

**Cross-origin browsers, sibling subdomains included.** A page on another origin can make the user's browser send requests that carry the user's cookies. For a browser request, the same-origin check (§HTTP request checks step 4, the same for upgrades) proves the page that sent it is on the app's own origin or one listed in `origins`: browsers set `Origin` and `Sec-Fetch-Site`, and pages can't. A sibling subdomain is `same-site`, so it's refused; `SameSite` cookies don't separate siblings, this check does. Over HTTP, `application/json` isn't a CORS-safelisted type, so the requests a cross-origin page can send without a preflight, such as form posts, fail step 3 first. The check proves nothing about script running on the app's own origin: injected script there calls every procedure as the user. Each `origins` entry is trusted as fully as the app's own origin, since its pages call every procedure with the user's cookies: list only exact origins the application controls. Never list `"null"`: browsers send `Origin: null` from sandboxed frames, `data:` documents and other opaque origins any site can create. There's no wildcard, pattern or reflection of the request's `Origin`, and the application must not build one by deriving `origins` from the request. An `origins` entry only passes Launch's own check. A cross-origin HTTP RPC or stream is a JSON `POST`, so the browser first sends a CORS preflight (`OPTIONS`), which Launch refuses like any other method, and then needs CORS headers to read the response: both are the host's to answer, and Launch sets none. A channel has no such barrier: a page on an `origins` entry sends and receives over its accepted WebSocket without CORS. Risk: an `origins` entry the application doesn't control, or `"null"`, high / possible.

**Slow, stalled and many peers.** Launch applies backpressure and credit limits to what it sends for one call; §Streams "Wire" and §Channels "Flow control" give their bounds and the frames they don't gate. A stream pulls its handler only as the reader reads and skips keep-alives while the reader is behind (§Streams "Wire"). A channel's credit windows and buffer mark regulate what it sends and bound the messages it holds unread, as parsed values, which take more memory than their bytes (§Channels "Flow control", "Node glue"). The host owns the rest, and Launch has no setting for it: an HTTP RPC's body is read whole, with no size or time limit, before any stage runs; a channel's input arrives in its upgrade URL, outside `maxPayload`; each open stream or channel holds a connection, or over HTTP/2 a stream within one, for as long as it runs. The host or a proxy in front of it limits request body bytes and read time, request target and header size, read and idle deadlines, concurrent connections and concurrent in-flight requests and open streams and channels, per client and in total (over HTTP/2 a connection cap alone doesn't bound them), request rates and CPU. Body-consuming parser middleware isn't the place: it consumes the body `handleRequest` reads. What the application puts in those frames is its to size: the values a handler yields, and the error data and schema issues a terminal failure frame carries. Strict JSON checking walks values recursively, so an input nested deeper than the engine's call stack allows (several thousand levels) answers `INTERNAL`, logged, instead of `INVALID_INPUT`, before any stage; the process keeps running, and the host's body limit bounds the cost. That's a limitation, not a planned depth limit. Risk without host limits: one unauthenticated caller exhausts the server's memory or connections before any stage runs, high / possible.

**Cancellation.** Signals are advisory (§Generated client "Calls"). When a client leaves, the call's signal aborts (over HTTP through the request's signal and the documented close wiring, on a channel through the socket), but stages, middleware, schemas and handlers that don't pass it on keep running and keep what they hold, and a write may already have committed. A peer that opens calls and leaves costs whatever uncooperative work each started, and a channel's received messages are still delivered after it closes. Risk: I/O that ignores the signal turns abandoned calls into held resources, medium / possible.

**Malicious response source.** The browser client trusts the server that answers its relative `/_rpc/` calls, the page's own origin; serve it over HTTPS. Clients check frames structurally (exact shapes, strict JSON, declared codes, root-relative redirects) and never recognize a malformed one as a failure or outcome: a stream or channel rejects with a `TypeError`, and an HTTP call keeps its original error (§Outcomes). Frames aren't signed, results aren't checked against schemas, and the stream and channel parsers have no size ceiling: a compromised server or a network attacker on plain HTTP can deliver any well-formed value or exhaust the tab. That attacker already controls the page, so Launch adds no defense against it. Results stay JSON data: Launch evaluates no frame and writes none as HTML. Rendering results safely is Angular's and the application's. Results carry untrusted data from an honest server too, such as keys users chose and the server stored: the TanStack integration's generated `structuralSharing` keeps an own `"__proto__"` key as data, but a `structuralSharing` override, or a function as the `QueryClient` default, replaces it and must keep the key itself (§TanStack Query integration).

**Caches.** An RPC reply's `Cache-Control: private, no-store` doesn't govern the page it was rendered into: server-rendered HTML can carry the results of the calls made while rendering, and its caching is the host's and the application's (§SSR, hydration and prerendering). Transfer only intentionally browser-visible DTOs and keep personalized HTML out of public and shared caches. Generated query keys hold the procedure and its input, not the user: give each server render its own `QueryClient`, as the TanStack Query guide's factory does, and clear or replace the browser's client when the signed-in user or tenant changes. Risk: personalized HTML in a shared cache, or a query cache kept across users, shows one user's data to another, high / possible.

**Remembered search values.** A `searchCookies()` cookie is client-controlled input, like the URL it's restored into: it's never `HttpOnly`, so any script on the origin reads and writes it, and a sibling subdomain can set a cookie of the same name for the parent domain. The router parses it with the key's codec, forgets a value the codec rejects, and writes an accepted one into the URL, so stages and handlers see it only as a search parameter (router SPEC §7 "Remembered search keys"). Keep secrets and personal data out of remembered keys. Risk: a remembered key holding sensitive data is readable by any script on the origin and persists for `maxAge`, medium / unlikely (a guess: remembered keys are meant for view state).

**Trusted server process and dependencies.** Everything in the server process is trusted: authored routes, stages, schemas and handlers, Launch, Angular and every dependency. The `Symbol.for` brands (outcomes, the request scope, the upgrade-listener slot) and a scope's binding to its application and Angular's `REQUEST` catch wiring mistakes across bundle copies; any code in the process can read or forge them, so they aren't isolation. The upgrade-listener slot is process-global and latest-wins: one application per process. Generation reads sources statically and runs no authored module, but it runs installed tooling (TypeScript, Angular's builders and, with `translateSegments`, `@angular/localize`'s tools), so it is as trusted as the dependency tree.

**The browser build graph.** Everything the browser build contains is public: namespace and procedure names, declared error codes and messages, route identities and static words included. Route copies strip server steps by liveness, not taint: a stripped step takes with it only the imports and statements nothing kept still uses (§Generated client "Bundles"). Side-effect imports and other untouched top-level statements stay. Here the copy keeps `import { todoTitle } from "./todos.data"`, so the browser loads `todos.data.ts`, its top-level code and everything it imports, the database client included:

```ts
// src/routes/todos/route.ts
import todos, { todoTitle } from "./todos.data"; // todos.data.ts also creates the database client

export default defineRoute("todos", { parent })
  .remote(({ query }) => ({ todos: { list: query({ handler: () => todos.list() }) } }))
  .title(() => todoTitle());
```

The router rejects a copy that keeps a direct `node:` or `*.server.*` import, but not what a kept import reaches (router SPEC §Import rule). Secrets belong in modules the browser graph never imports: ones only stripped steps and the server entry import. Risk: a secret in a module a copy keeps ships in the public build, critical / possible.

**Development server.** `ng serve` is for trusted networks: it serves sources and dev tooling, forwards channels through a process-global slot, and has no access control beyond the host check. Don't expose it to an untrusted network, such as by binding it to `0.0.0.0`. Risk: high / possible.

## Exclusions

Each section above names what it leaves out. Across the package, Launch doesn't provide:

- Server-side storage adapters or durability across server restarts; persistence is the handler's job. (`searchCookies()` keeps the router's remembered search keys in browser cookies; see §Remembered search keys.)
- Production authentication, CORS, caching or deployment policy. HTTP RPCs are host-checked and refused unless proven same-origin (§HTTP request checks); there's no CSRF token scheme. §Threat model says what the host and the application must provide.
- Enforcement of the browser/server module boundary beyond what route copies import (§Generated client).
- Tested support for hosts and runtimes other than those §Runtimes, §Streams and §Channels name, and deploy adapters for them.

## Decided limitations

Decided on 2026-11-13, before 0.1. Not planned:

- **Success statuses other than 200.** A result is always 200; statuses come from failures and outcomes (§Outcomes). Only things watching the wire would see a 201 or 204, and a 204 would need an empty-body rule for results.
- **Mapping `FORBIDDEN` to a page.** A stage that guards a page's reads throws `redirect` for a signed-out visitor and `notFound` for something the visitor mustn't see (§Outcomes). A page that must answer 403 isn't covered: redirecting to a page shows it, without the status.
- **Redirects that leave the app.** `redirect` and `RpcRedirect.to` stay root-relative. An external destination, such as the start of an OAuth flow, is a mutation's result that the page passes to `location.assign`; mutations don't run during rendering, and outcomes act only in navigation.
