# Personal todos: native Launch consumer

A bounded read/write consumer using actual static generation, not handwritten generated route modules or routes. Requires built workspace packages.

```sh
pnpm --filter 'angular-launch-consumer...' build   # the router, Launch, then this example
pnpm --dir examples/angular-launch verify /absolute/absent/evidence
```

`verify` builds the `verification` configuration and the `verification-development` one (unoptimized, so Angular's development checks run), starts the first's built server on a free loopback port and runs `verify.mjs` against it, and the remembered-search-key rows in `verify-remembered.mjs` against both; CI's `launch-browser` job runs the same two commands. To look around by hand, run `node examples/angular-launch/dist/todos/server/server.mjs`, which prints `LAUNCH_READY http://127.0.0.1:PORT`.

The loopback server uses **test-only** `proof-user=alice` / `proof-user=bob` cookies and an in-memory database. It is not production authentication or deployment infrastructure. Server behavior lives on the routes, in `src/routes/**/route.ts`, each importing `defineRoute` from `@loozo/angular-launch`:

- The root route's `.context()` stage reads the cookie and returns the context every procedure starts from: `user` (or `null`), the database and the proof counters. A stage runs at most once per request scope, and only when a call needs it, so a page that makes no RPC runs none.
- The pathless `+authenticated` group, which holds the pages that need a user (`/todos`, `/todo/$id`, `/uncached`, `/identity`, `/live`), has a stage that throws `redirect(signIn, {})` for a call without a user, before input validation, and narrows `user` below it. `signIn` is the sign-in route's `destination` from its `destination.generated.ts`, so a signed-out `/todos` answers 302 to `/sign-in`. The group declares the `session` namespace with `.remote()` and runs a `timing` middleware around it with `.use()`, which adds a `server-timing` header; a call its stage redirects never reaches the middleware, so it carries no header. `session.current` sets a test-only `proof-seen` cookie, which reaches the page response when a resolver calls it during server rendering.
- `todos`, `todo/$id` and `live` declare their own namespaces below that group. Their resolvers and pages call them, and `session`, through `remote`.
- `identity` declares nothing: its page reads its ancestor's `session.current` through `injectRoute().queries`.
- The `+authenticated` group declares a `density` search key, and `todos` its `pageSize` and `filter`, each `retained` and `remembered`, so the page's links carry them and they come back on the next visit. `config.ts` stores them with Launch's `searchCookies()`, so the server renders them: a bare `/todos` with a remembered page size answers 302 to `/todos?pageSize=50`. The todos resolver passes the filter to `todos.filter` as input, whose handler throws `notFound()` for a filter that no longer exists (`archived`), so a remembered `archived` renders `/todos` with the `all` fallback, 200, and deletes the cookie.

Visit `/todos`, `/todo/alice-initial`, `/live`, `/identity`, `/uncached`, `/about` or `/static`; dark mode is the default.

`/about` declares the public `about` namespace, which has no stage of its own and answers the same for everyone: `about.summary` through a resolver and `about.limits` through `injectQuery`. The `prerender` configuration prerenders it, and the RPC-free `/static`, at build time: its calls run with a context the root stage builds from a cookie-less `GET` of the page's URL, their results go into the file, and loading it makes no RPC. A client-side navigation to it calls the server like any other page.

`/todo/$id` shows one todo through its resolver's `todo.get`, which throws `notFound()` for a missing or another user's todo. The app's `provideRouter` uses `withNavigationErrorHandler(rpcNavigationErrors({ notFound: createUrl(notFound, {}) }))`, `notFound` being the not-found route's generated `destination`, so the server renders `/not-found` with status 404 at the requested URL, and client navigation shows it without changing the address. Hydrating that page calls `todo.get` once more over HTTP, because only successes transfer.

The server's maintenance rule is `angular.handle(scope.request, scope)`, with `scope` from the generated `createRequestScope(web)`, which runs no stage itself. It passes one loopback `allowedHosts` list to both `AngularNodeAppEngine` and `handleRequest`; `verify.mjs` sends `Origin` on its Node `fetch` RPC calls, which send neither `Origin` nor `Sec-Fetch-Site` by themselves. The private request token survives Angular's proxy-header sanitization clone; it is never added to browser RPC headers. This detects wrong app/request/scope pairing, not incorrect authentication or arbitrary server code.

Generation runs with `tanstackQuery: true`, and the app provides `provideTanStackQuery(() => new QueryClient())` and `provideLaunchQueries()` with TanStack's default `staleTime: 0`. The todos page reads `todos.list` through `injectQuery` and writes through `injectMutation`; the todos resolver still calls its pathless ancestor's `session.current` directly. Both use the one request scope per HTML request, so the root stage runs once. Hydration makes no RPC: TanStack hydrates the list from its own state in the HTML, and the resolver reuses its native POST transfer cache entry. Refresh after stability refetches over real HTTP with a fresh context. `/identity` reads `session.current` only through `injectQuery`. Authored `route.ts` files (stages, middleware, handlers), `server.generated.ts`, and database and schema modules never enter the browser graph: pages import each route's generated browser copy.

`/live` shows the same user's todos from the `live` namespace: its resolver reads `live.snapshot`, a query, so the server renders the list, and after hydration the page follows `live.watch`, a stream that yields the list now and after every write, with `connect()`, until the page goes away. A todo added on `/todos` in another tab appears there without a reload. Its form adds titles over `live.add`, a channel that yields the list first and again after each title it adds; the page runs it with `connect()` too, and the server entry creates the websocket upgrade listener at module top level, where `ng serve`'s serve builder finds it too. The `live.ticks` stream is a loopback proof fixture that counts values and can end with its declared `STOPPED` error.

The labelled native form adds trimmed titles of 1–200 characters; the form is disabled while the add is pending, and failed input is retained. Complete sets an owned todo's `completed` state to true idempotently (it does not toggle), and Delete removes it. Both are optimistic: the row changes at once and the form and other rows stay usable (the row itself and Refresh wait for the write, since another write to it or a read would undo its optimistic state), the writes share a mutation scope so the server gets them in order, and a failed write undoes its own row. The declared error decides how: a todo deleted elsewhere answers `NOT_FOUND`, and its row drops out instead of coming back. After every write, succeeded or not, the `MutationCache` in `config.ts` reads every Launch query on screen again, once the last pending write settles, and the write stays pending until then. If that read fails, the page keeps what it shows, reports the write, and says the list may be out of date. Status feedback is live. The per-user in-memory store survives **browser refresh**, not server restart. Foreign/missing IDs return declared `NOT_FOUND` with `{id}` and do not change either user's rows.

The `build` target uses `@loozo/angular-launch:application`, so every build configuration generates first. `pnpm check` (`ng run todos:build:check`) checks the generated files without writing, then builds. `pnpm serve` runs `ng serve` through `@loozo/angular-launch:serve`, which regenerates as you edit. Outputs are ignored and owned by the genuine generator. Do not format generated outputs independently.

Native qualification:

```sh
pnpm --dir examples/angular-launch exec ng run todos:build:prerender           # emits /about and /static
pnpm --dir examples/angular-launch exec ng run todos:build:prerender-signed-in # prerenders /identity; must exit nonzero
```

The `verification` configuration uses a test-only browser entry exposing cancellation, typed-error and client-navigation hooks, not extra product UI; the normal entry has no hooks. The hooks reach clients through `injectActiveRoute()`, read once at bootstrap and narrowed with `is()` when a hook runs, so each needs its page active. A test-only delay cookie makes the same read slow enough to prove native HTTP cancellation. The server entry aborts the handler's `signal` when the response closes unfinished, and the list handler records that it saw the abort; the read itself doesn't take the signal and still finishes. The loopback-only `proof-failure` cookie exercises generic unexpected-failure normalization; private exception details never appear in the client frame. `proof-ssr-failure` fails the list only while rendering HTML, so the browser's own call succeeds. Cancelled writes may already have committed; there is no rollback guarantee.

`verify.mjs` uses Playwright's Chromium (`pnpm --dir packages/angular-launch exec playwright install chromium`) and saves private HTML, request/context, cancellation and browser-closure evidence, the servers' output and screenshots only in the supplied new directory. Package tests cover generator scopes, mutation kinds, async schema input/output typing, semantic prepublication, genuine factory provenance, procedure-owned declared errors, actual native SSR mutation denial and runtime boundaries. Browser verification includes zero load-time RPCs with `staleTime: 0` (with a client-navigation control that does refetch), each user's todos in the server-rendered list even with a slow handler, TanStack state in the HTML without a duplicate HTTP transfer entry, keyboard add → optimistic complete → reload with each write reading the list again, optimistic complete and delete rolling back by declared error (a todo deleted elsewhere drops out on `NOT_FOUND`, a failed delete comes back in place), two writes started together reaching the server in order with one read after both (also for an add and a complete in different scopes), the row and Refresh disabled while a write is pending, a write whose list read fails keeping its row with a stale-list notice, a click before hydration replayed once, a failed server query loading in the browser, second-user isolation, invalid input and signed-out writes (redirected to sign in) never writing, the built server refusing foreign hosts and RPCs not proven same-origin without running a stage, a page without RPCs running no stage, cookies and headers on RPC responses (none on a call its stage redirects) and the rendered page's cookie without its headers, a bare leaf's narrowed active handle calling its ancestor's procedure, `live.ticks`'s `INVALID_INPUT` reaching the browser as an `RpcError`, a todo added over RPC showing in the next server-rendered `/todos` (pages and RPCs share the server's in-memory database), typed declared payloads, generic failures and one batched desktop/narrow screenshot pass. It checks outcomes too: `todo.get` and `session.current` answer 404 and 303 frames over HTTP without `Location`, a signed-out `/todos` is a 302 to `/sign-in`, foreign and missing todos render the not-found page with 404, that page hydrates at its URL with one `todo.get` call and no console errors, and client navigation renders not-found in place and follows the sign-in redirect. It also checks that `/live` renders its list on the server, follows the stream after hydration without keeping the app unstable and shows a write made elsewhere, and that the browser stream client yields typed values, rejects with the declared `STOPPED` error and closes the request on `break`, which aborts the handler's signal and returns it. Clients leaving a stream, a page following one or a page render that's still loading are expected, so the built server must log nothing for them while still logging real failures, and its abort handling must match the snippets in Launch's [Aborted requests](../../packages/angular-launch/README.md#aborted-requests). For the channel, it checks that the page's form adds a title over the socket and shows the channel's and the stream's updated lists while the app stays stable, that the raw channel client yields the lists in order while sending, rejects a refused title with its `INVALID_INPUT` issues and closes the socket on `break` (the handler's signal aborts and it returns), and that the built server answers foreign-origin and input-less upgrades over plain HTTP without running a stage. For remembered search keys, against both builds, it checks the restore's 302 with the RPC's cookie, a stale filter answering 200 with the fallback and one deletion (and two owners both deleted), a missing todo staying a 404 at its URL after one retry, a signed-out redirect keeping the value, the ordinary 404 without a restore, and in Chromium the same through hydration and client navigation, links keeping retained keys and every commit writing the browser's cookie. It runs Launch's [recovery fixture](../../packages/angular-launch/tests/fixtures/remembered/README.md) too, which builds its own app. It finally runs the prerender builds: `/about` must contain both build-time results and their transfer state, be served as the file with no RPC while loading and call the server after a client-side navigation to it, and prerendering `/identity` must fail, naming `session.current`'s redirect. There is no production auth/CORS policy.
