# Personal todos: native Launch consumer

A bounded read/write consumer using actual static generation, not handwritten generated facades or routes. Requires built workspace packages.

```sh
pnpm --filter @loozo/angular-router build
pnpm --filter @loozo/angular-launch build
pnpm --dir examples/angular-launch build
pnpm --dir examples/angular-launch exec ng run todos:build:verification
node examples/angular-launch/dist/todos/server/server.mjs
# LAUNCH_READY http://127.0.0.1:PORT
node examples/angular-launch/verify.mjs http://127.0.0.1:PORT /absolute/absent/evidence
```

The loopback server uses **test-only** `proof-user=alice` / `proof-user=bob` cookies and an in-memory database. It is not production authentication or deployment infrastructure. The `todos` and `live` groups list the `signedIn` middleware, which refuses calls without a test user with `FORBIDDEN` before input validation and narrows `user` for the handlers. The `session` and `todo` groups, which pages read while navigating, list `signInFirst` instead: it throws `redirect(createUrl(signIn, {}))`, so a signed-out `/todos` answers 302 to `/sign-in`. The `session` group also lists a `timing` middleware that adds a `server-timing` header, and `session.current` sets a test-only `proof-seen` cookie, which reaches the page response when a resolver calls it during server rendering. Visit `/todos`, `/todo/alice-initial`, `/live`, `/identity`, `/uncached` or `/static`; dark mode is the default.

`/todo/$id` shows one todo through its resolver's `todo.get`, which throws `notFound()` for a missing or another user's todo. The app's `provideRouter` uses `withNavigationErrorHandler(rpcNavigationErrors({ notFound: createUrl(notFound, {}) }))`, so the server renders `/not-found` with status 404 at the requested URL, and client navigation shows it without changing the address. Hydrating that page calls `todo.get` once more over HTTP, because only successes transfer.

The server's maintenance rule is `angular.handle(scope.request, scope)`, using the generated app binding. It passes one loopback `allowedHosts` list to both `AngularNodeAppEngine` and `handleRequest`; `verify.mjs` sends `Origin` on its Node `fetch` RPC calls, which send neither `Origin` nor `Sec-Fetch-Site` by themselves. The private request token survives Angular's proxy-header sanitization clone; it is never added to browser RPC headers. This detects wrong app/request/scope pairing, not incorrect authentication or arbitrary server code.

Generation runs with `tanstackQuery: true`, and the app provides `provideTanStackQuery(() => new QueryClient())` and `provideLaunchQueries()` with TanStack's default `staleTime: 0`. The todos page reads `todos.list` through `injectQuery` and writes through `injectMutation`; the todos resolver still calls ancestor/pathless `session.current` directly. Both use the one context value per HTML request. Hydration makes no RPC: TanStack hydrates the list from its own state in the HTML, and the resolver reuses its native POST transfer cache entry. Refresh after stability refetches over real HTTP with a fresh context. `/identity` reads `session.current` only through `injectQuery`. Context, handler, database and schema modules never enter the browser graph.

`/live` shows the same user's todos from the `live` group: its resolver reads `live.snapshot`, a query, so the server renders the list, and after hydration the page follows `live.watch`, a stream that yields the list now and after every write, until the page goes away. A todo added on `/todos` in another tab appears there without a reload. The `live.ticks` stream is a loopback proof fixture that counts values and can end with its declared `STOPPED` error.

The labelled native form adds trimmed titles of 1–200 characters; the form is disabled while the add is pending, and failed input is retained. Complete sets an owned todo's `completed` state to true idempotently (it does not toggle), and Delete removes it. Both are optimistic: the row changes at once and the form and other rows stay usable (the row itself and Refresh wait for the write, since another write to it or a read would undo its optimistic state), the writes share a mutation scope so the server gets them in order, and a failed write undoes its own row. The declared error decides how: a todo deleted elsewhere answers `NOT_FOUND`, and its row drops out instead of coming back. After every write, succeeded or not, the `MutationCache` in `config.ts` reads every Launch query on screen again, once the last pending write settles, and the write stays pending until then. If that read fails, the page keeps what it shows, reports the write, and says the list may be out of date. Status feedback is live. The per-user in-memory store survives **browser refresh**, not server restart. Foreign/missing IDs return declared `NOT_FOUND` with `{id}` and do not change either user's rows.

The `build` target uses `@loozo/angular-launch:application`, so every build configuration generates first. `pnpm check` (`ng run todos:build:check`) checks the generated files without writing, then builds. `pnpm serve` runs `ng serve` through `@loozo/angular-launch:serve`, which regenerates as you edit. Outputs are ignored and owned by the genuine generator. Do not format generated outputs independently.

Native qualification:

```sh
pnpm --dir examples/angular-launch exec ng run todos:build:prerender # prerenders /identity; must exit nonzero
pnpm --dir examples/angular-launch exec ng run todos:build:static    # emits /static/index.html
```

The `verification` configuration uses a test-only browser entry exposing cancellation, typed-error and client-navigation hooks, not extra product UI; the normal entry has no hooks. A test-only delay cookie makes the same read slow enough to prove native HTTP cancellation. The server entry aborts the handler's `signal` when the response closes unfinished, and the list handler records that it saw the abort; the read itself doesn't take the signal and still finishes. The loopback-only `proof-failure` cookie exercises generic unexpected-failure normalization; private exception details never appear in the client frame. `proof-ssr-failure` fails the list only while rendering HTML, so the browser's own call succeeds. Cancelled writes may already have committed; there is no rollback guarantee.

`verify.mjs` uses `/usr/bin/chromium` and saves private HTML, request/context, cancellation and browser-closure evidence only in the supplied new directory. Package tests cover generator scopes, mutation kinds, async schema input/output typing, semantic prepublication, genuine factory provenance, procedure-owned declared errors, actual native SSR mutation denial and runtime boundaries. Browser verification includes zero load-time RPCs with `staleTime: 0` (with a client-navigation control that does refetch), each user's todos in the server-rendered list even with a slow handler, TanStack state in the HTML without a duplicate HTTP transfer entry, keyboard add → optimistic complete → reload with each write reading the list again, optimistic complete and delete rolling back by declared error (a todo deleted elsewhere drops out on `NOT_FOUND`, a failed delete comes back in place), two writes started together reaching the server in order with one read after both (also for an add and a complete in different scopes), the row and Refresh disabled while a write is pending, a write whose list read fails keeping its row with a stale-list notice, a click before hydration replayed once, a failed server query loading in the browser, second-user isolation, invalid/denied no-write checks, the built server refusing foreign hosts and RPCs not proven same-origin without creating a context, cookies and headers on RPC responses and the rendered page's cookie without its headers, typed declared payloads, generic failures and one batched desktop/narrow screenshot pass. It checks outcomes too: `todo.get` and `session.current` answer 404 and 303 frames over HTTP without `Location`, a signed-out `/todos` is a 302 to `/sign-in`, foreign and missing todos render the not-found page with 404, that page hydrates at its URL with one `todo.get` call and no console errors, and client navigation renders not-found in place and follows the sign-in redirect. It also checks that `/live` renders its list on the server, follows the stream after hydration without keeping the app unstable and shows a write made elsewhere, and that the browser stream client yields typed values, rejects with the declared `STOPPED` error and closes the request on `break`, which aborts the handler's signal and returns it. It finally runs the prerender build, which must fail for `/identity`. There is no storage adapter or production auth/CORS policy.
